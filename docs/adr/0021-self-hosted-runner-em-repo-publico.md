## Context / Contexto

**EN:** This repository has one self-hosted CI runner, driving `.github/workflows/heavy.yml`'s four jobs (`sanitize` and `fonteng`, each a `backend: [ON, OFF]` matrix). It is a public repository. GitHub's own documentation says this combination should almost never exist. This ADR names why the runner exists, cites the official guidance verbatim, records the líder's decision as an **accepted risk** (not a claim of compliance), and lists the compensating controls with an honest statement of which ones are actually verified today and which are not.

**Why a self-hosted runner exists here — verified against `heavy.yml` and `AGENTS.md`, not presumed.** The initial framing offered for this ADR was that the heavy sanitizer/font-engine work "doesn't fit the hosted runner's time/resource budget." **That framing does not hold up under the file's own text and was corrected before writing this ADR:**

1. **Continuity from the Forgejo era, not a resource ceiling.** `sanitize` and `fonteng` ran on the retired Forgejo runner `claudio` before this project left Codeberg on 2026-07-25 (`.forgejo/` deleted, `claudio` decommissioned). `GH-ONLY-RUNNER` (`TODO.md`) ported the existing recipe to a new, GitHub-native self-hosted runner rather than dropping the gates outright — the runner's origin is **preserving work that already existed**, not a discovery that GitHub-hosted infrastructure could not do the job.
2. **Both `heavy.yml` jobs are additive distro/toolchain legs that GitHub-hosted runners already run the equivalent of, successfully, today.** `heavy.yml`'s own header comment: *"[sanitize] Default compiler on this image, which is gcc — matching what the retired recipe built. `.github/workflows/nightly.yml` keeps running the same gate nightly on `ubuntu-latest`, so this is the Fedora/gcc leg, **not a replacement**."* Confirmed by reading `nightly.yml`: it runs the identical ASan/LSan/UBSan `backend: [ON, OFF]` matrix on `ubuntu-latest` with the default (gcc) compiler, on a schedule, on GitHub-hosted infrastructure, successfully. Symmetrically, `ci.yml`'s `build-and-test-fonteng` job already runs the equivalent `GLINTFX_OWN_FONT_ENGINE=ON` matrix on `ubuntu-latest` pinned to clang, on every push/PR. **So the self-hosted runner does not carry work the hosted runner is incapable of** — it carries a **Fedora** leg of both gates, the same doctrine as `distro-matrix.yml`'s `CI-DISTROMATRIX` effort (catch distro/toolchain-specific drift — the project's own precedent is the historical g++-vs-clang++ `[[deprecated]]` divergence cited in that file).
3. **One property a shared, ephemeral, GitHub-hosted VM genuinely cannot offer: a machine stable enough for a strict, baseline-relative performance gate.** `TODO.md`'s `PERF-D2D3`/`GH-ONLY-RUNNER` items record that `draw2d_perf_budget.cpp`'s strict tier (`GLINTFX_PERF_STRICT`, 1.5x-of-baseline) needs a **fixed, non-shared** machine to calibrate against — a hosted runner's CPU class and load vary run to run in ways a 1.5x comparison cannot tolerate. ⚠️ **Honesty check, done before writing this paragraph:** `grep GLINTFX_PERF_STRICT .github/workflows/heavy.yml` finds only the file's own comment explaining that this variable is **deliberately NOT set today** (`heavy.yml`'s own words: *"It is deliberately NOT set on this runner. Those baselines were measured on an unconstrained machine ... this container is capped at 4 CPUs, so the strict tier would fail on the cap, not on a regression."*). **This justification is real but currently latent, not exercised** — the runner is a candidate stable machine for a future recalibration, not something actively using that property today.

**The concrete risk this ADR exists to name, from GitHub's own documentation** (fetched 2026-08-06, `docs.github.com/en/actions/reference/security/secure-use`): **"self-hosted runners should almost never be used for public repositories on GitHub, because any user can open pull requests against the repository and compromise the environment"**, and self-hosted runners **"do not have guarantees around running in ephemeral clean virtual machines, and can be persistently compromised by untrusted code in a workflow."** GitHub's runner-group access-policy documentation (`docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access`) goes further still, independent of trigger: **"We recommend that you only use self-hosted runners with private repositories. This is because forks of your public repository can potentially run dangerous code on your self-hosted runner machine."** The same page states that a runner group's **default access policy already restricts self-hosted runners to private repositories only** — an organization must take an explicit, opt-in action to let a self-hosted runner attach to *any* public repository, independent of what triggers that workflow declares.

**PT:** Este repositório tem um runner de CI self-hosted, que aciona os quatro jobs do `.github/workflows/heavy.yml` (`sanitize` e `fonteng`, cada um numa matrix `backend: [ON, OFF]`). É um repositório público. A própria documentação do GitHub diz que esta combinação quase nunca deveria existir. Esta ADR nomeia por que o runner existe, cita a orientação oficial literalmente, registra a decisão do líder como um **risco aceito** (não uma alegação de conformidade), e lista os controles compensatórios com uma declaração honesta de quais são de fato verificados hoje e quais não são.

**Por que existe um runner self-hosted aqui — verificado contra o `heavy.yml` e o `AGENTS.md`, não presumido.** O enquadramento inicial oferecido para esta ADR era que o trabalho pesado de sanitizer/motor-de-fonte "não cabe no orçamento de tempo/recurso do runner hospedado." **Esse enquadramento não se sustenta no próprio texto dos arquivos e foi corrigido antes de escrever esta ADR:**

1. **Continuidade da era Forgejo, não teto de recurso.** `sanitize` e `fonteng` rodavam no runner Forgejo `claudio`, aposentado, antes deste projeto sair do Codeberg em 2026-07-25 (`.forgejo/` apagado, `claudio` desligado). O `GH-ONLY-RUNNER` (`TODO.md`) portou a receita existente pra um runner self-hosted novo, nativo do GitHub, em vez de simplesmente derrubar os gates — a origem do runner é **preservar trabalho que já existia**, não uma descoberta de que a infraestrutura hospedada do GitHub não daria conta.
2. **Os dois jobs do `heavy.yml` são pernas ADICIONAIS de distro/toolchain que runners hospedados do GitHub já rodam o equivalente, com sucesso, hoje.** O próprio comentário de cabeçalho do `heavy.yml`: *"[sanitize] Compilador default desta imagem, que é o gcc -- batendo com o que a receita aposentada buildava. O `.github/workflows/nightly.yml` segue rodando o mesmo gate toda noite no `ubuntu-latest`, então esta é a perna Fedora/gcc, **não uma substituição**."* Confirmado lendo o `nightly.yml`: ele roda a matrix idêntica ASan/LSan/UBSan `backend: [ON, OFF]` no `ubuntu-latest` com o compilador default (gcc), em agendamento, em infraestrutura hospedada do GitHub, com sucesso. De forma simétrica, o job `build-and-test-fonteng` do `ci.yml` já roda a matrix equivalente `GLINTFX_OWN_FONT_ENGINE=ON` no `ubuntu-latest` fixado em clang, em todo push/PR. **Então o runner self-hosted não carrega trabalho que o runner hospedado é incapaz de fazer** -- ele carrega uma perna **Fedora** dos dois gates, a mesma doutrina do esforço `CI-DISTROMATRIX` do `distro-matrix.yml` (pegar deriva específica de distro/toolchain -- o precedente do próprio projeto é a divergência histórica `[[deprecated]]` g++-vs-clang++ citada naquele arquivo).
3. **Uma propriedade que uma VM hospedada, efêmera e compartilhada genuinamente não consegue oferecer: uma máquina estável o bastante para um gate de performance estrito e relativo-à-baseline.** Os itens `PERF-D2D3`/`GH-ONLY-RUNNER` do `TODO.md` registram que o nível estrito do `draw2d_perf_budget.cpp` (`GLINTFX_PERF_STRICT`, 1,5x-da-baseline) precisa de uma máquina **fixa, não-compartilhada** pra se calibrar contra -- a classe de CPU e a carga de um runner hospedado variam de execução pra execução de formas que uma comparação de 1,5x não tolera. ⚠️ **Checagem de honestidade, feita antes de escrever este parágrafo:** `grep GLINTFX_PERF_STRICT .github/workflows/heavy.yml` só acha o próprio comentário do arquivo explicando que essa variável está **deliberadamente NÃO setada hoje** (palavras do próprio `heavy.yml`: *"NÃO é setada neste runner, de propósito. Aquelas baselines foram medidas numa máquina sem limite ... este container é limitado a 4 CPUs, então o nível estrito falharia pelo teto, não por regressão."*). **Esta justificativa é real mas hoje LATENTE, não exercitada** -- o runner é candidato a máquina estável pra uma futura recalibração, não algo que usa essa propriedade ativamente hoje.

**O risco concreto que esta ADR existe para nomear, da própria documentação do GitHub** (extraída em 2026-08-06, `docs.github.com/en/actions/reference/security/secure-use`): **"self-hosted runners should almost never be used for public repositories on GitHub, because any user can open pull requests against the repository and compromise the environment"**, e runners self-hosted **"do not have guarantees around running in ephemeral clean virtual machines, and can be persistently compromised by untrusted code in a workflow."** A documentação de política de acesso de grupo de runner do GitHub (`docs.github.com/en/actions/how-tos/manage-runners/self-hosted-runners/manage-access`) vai ainda mais longe, independente de gatilho: **"We recommend that you only use self-hosted runners with private repositories. This is because forks of your public repository can potentially run dangerous code on your self-hosted runner machine."** A mesma página afirma que a **política de acesso default de um grupo de runner já restringe runners self-hosted a repositórios privados apenas** -- uma organização precisa de uma ação explícita, opt-in, para deixar um runner self-hosted anexar em *qualquer* repositório público, independente do que aquele workflow declara como gatilho.

## Decision / Decisão

**EN:** The líder (petrus), on 2026-08-06, reviewing the finding above, decided: **register this as an accepted risk, with the compensating controls listed below** — not as a claim that this configuration is compliant with GitHub's own recommendation, because it is not. The self-hosted runner continues to serve `heavy.yml` on this public repository. This is a **deliberate, narrower exception** to GitHub's blanket "don't," justified by: (a) removing the specific, officially-named attack path (a fork's pull request reaching the runner) via a trigger that structurally excludes `pull_request`; (b) hardening the container substantially beyond what GitHub's platform guarantees for any self-hosted runner; and (c) the practical fact that the one alternative GitHub actually recommends — a private repository, or no self-hosted runner at all — is incompatible with this project's own, separately-decided goal of broad public distribution (`ADR-0015` framework2d direction, `ADR-0019` Apache-2.0 rotation for wide adoption). This is a **risk accepted**, not a **risk mitigated to zero**, and not a **conformant configuration**.

**PT:** O líder (petrus), em 2026-08-06, revisando o achado acima, decidiu: **registrar isto como risco aceito, com os controles compensatórios listados abaixo** -- não como uma alegação de que esta configuração está em conformidade com a própria recomendação do GitHub, porque não está. O runner self-hosted continua servindo o `heavy.yml` neste repositório público. Isto é uma **exceção deliberada e mais estreita** ao "não faça" geral do GitHub, justificada por: (a) remover o caminho de ataque específico e oficialmente nomeado (um pull request de fork alcançando o runner) via um gatilho que exclui estruturalmente `pull_request`; (b) endurecer o container substancialmente além do que a plataforma do GitHub garante para qualquer runner self-hosted; e (c) o fato prático de que a única alternativa que o GitHub de fato recomenda -- um repositório privado, ou nenhum runner self-hosted -- é incompatível com o objetivo próprio e separadamente decidido deste projeto de distribuição pública ampla (direção framework2d do `ADR-0015`, rotação Apache-2.0 do `ADR-0019` para adoção ampla). Isto é um **risco aceito**, não um **risco mitigado a zero**, e não uma **configuração conforme**.

## Compensating controls / Controles compensatórios

**EN:** Every control below states what it prevents and how it is verified *today*. ⚠️ **A control without a verification mechanism is a promise, not a control** — where that is the case, it is stated plainly rather than folded into the surrounding reassurance.

**PT:** Todo controle abaixo declara o que impede e como é verificado *hoje*. ⚠️ **Controle sem mecanismo de verificação é promessa, não controle** -- onde é o caso, isso é dito às claras em vez de diluído na tranquilização ao redor.

| # | Controle | O que impede | Verificação hoje |
|---|---|---|---|
| 1 | **Sem gatilho `pull_request`** em `heavy.yml` (só `push: branches: [main]`, filtrado por paths, + `workflow_dispatch`) | O caminho de ataque primário e oficialmente nomeado pelo GitHub: um PR de fork rodando código no runner (a exploração "pwn request" da §7 da pesquisa deste ADR) | ✅ **AUTOMATIZADA, contínua.** `tools/check_workflow_self_hosted_gate.py`, rodado no passo `SEC-CI-HARDEN` do job `lint-and-scan` de `ci.yml`, em **todo push/PR**, num runner GitHub-hosted (nunca no self-hosted). Parseia estruturalmente o YAML com PyYAML (não `grep`, que casaria os próprios comentários explicativos do arquivo) e **falha o build** se qualquer job `self-hosted` também estiver sob um workflow com `pull_request`/`pull_request_target`/`issue_comment`. |
| 2 | **Actions de terceiro fixadas por SHA de commit completo** (`actions/checkout`, `actions/cache`, 4 pontos em `heavy.yml`), não pela tag mutável `@v4` | Um repositório de action comprometido (padrão tj-actions/changed-files 2025) reponteando uma tag e entregando código novo, malicioso, ao runner self-hosted na próxima execução | ⚠️ **NÃO AUTOMATIZADA hoje.** O pin existe no texto do arquivo (confirmado por leitura direta) e a verificação de que continua lá foi feita **manualmente**, por auditoria (`AUD-CI-RUNNER`, 2026-07-29) e por este próprio ADR -- **nenhum gate de CI re-confere que `heavy.yml` segue com `uses:` pinado por SHA**; um commit futuro que trocasse de volta pra `@v4` passaria sem alarme. |
| 3 | **`--cap-drop=ALL` + `--security-opt=no-new-privileges`** no container do runner (`tools/ci/runner_up.sh`) | Escalada de privilégio via operação de kernel privilegiada (mount, `ptrace`, socket raw) mesmo que código arbitrário já esteja executando dentro do container | 🟡 **APLICADA por construção, verificada em RUNTIME só UMA VEZ.** As flags são literais no script, aplicadas a cada início de container -- mas a confirmação de que o container *vivo* de fato tem zero capabilities veio de uma inspeção manual e pontual (`docker inspect` + `docker exec` read-only da `AUD-CI-RUNNER`, 2026-07-29), não de um gate que reconfira a cada execução. |
| 4 | **Tetos de recurso** -- `--memory=8g --memory-swap=8g` (swap zerado), `--cpus=4`, `--pids-limit=4096`, mais `-j2` literal (nunca `$(nproc)`) nos builds | OOM da própria máquina do líder por um build dentro do container; classe de DoS por fork-bomb de processo via `--pids-limit` | 🟡 **APLICADA por construção (cgroup do Docker, não opcional), não re-verificada por gate.** Nenhum passo de CI confirma que o teto ainda está em vigor a cada job; a evidência de que funciona é o pico medido histórico (3,17 GiB de 8 GiB, 39% do teto, `GH-ONLY-RUNNER`), não uma checagem contínua. |
| 5 | **Runner efêmero** (`--ephemeral`, um job e destruído; sem mount persistente; `systemd --user` reergue um container novo depois de cada job) | Estado sobrevivendo entre jobs -- um comprometimento no job N alcançando o job N+1, ou credencial/artefato deixado pra trás pra a próxima execução ler | 🟡 **APLICADA por construção (flag de registro `--ephemeral` do runner + container sem mount), verificada em RUNTIME só UMA VEZ.** A `AUD-CI-RUNNER` confirmou "genuinamente sem mount e portanto estruturalmente efêmero" por inspeção ao vivo -- pontual, não recorrente. |
| 6 | **`permissions: contents: read`** declarado explicitamente no topo de `heavy.yml` (o **único** dos 6 workflows deste repo que declara `permissions:`, ver tabela de conformidade da pesquisa-mãe) | Mesmo um comprometimento de supply-chain (via #2) ou de execução de código bem-sucedido herdar um `GITHUB_TOKEN` capaz de escrever no repositório (push, tag, release) | ⚠️ **NÃO AUTOMATIZADA hoje.** É uma declaração estática no YAML, visível em qualquer diff/review -- mas nenhum gate falha o build se um commit futuro ampliar essa permissão (ex.: pra `write-all`). |
| 7 | **Zero uso de `secrets.*`** em `heavy.yml` (confirmado por `grep`, ver §9 da pesquisa-mãe) | Um comprometimento dentro do container ter QUALQUER credencial pra exfiltrar -- nenhum segredo jamais é colocado no ambiente deste workflow | ⚠️ **NÃO AUTOMATIZADA como gate dedicado hoje.** O `gitleaks` do `lint-and-scan` (TST-L1-SECRETS) varre a árvore de código-fonte + histórico do git por strings com formato de segredo -- uma checagem diferente e mais ampla, não algo que confirme especificamente "`heavy.yml` continua sem `secrets.`". A confirmação de hoje veio de `grep` manual, na `AUD-CI-RUNNER` e nesta ADR. |
| 8 | **Sem chave `container:`** na composição do workflow -- o próprio runner É o container sandboxado | Uma saída via docker-in-docker ou socket do Docker montado, que a chave `container:` combinada com um runner self-hosted baseado em Docker poderia introduzir | ⚠️ **Só estática.** Visível no texto do YAML; nenhum gate confere isso hoje. |
| 9 | **Restrição de egress de rede** | Pivô de LAN (alcançar a rede doméstica do líder) caso os controles #1-#3 sejam derrotados juntos | 🔴 **AUSENTE, não implementado.** `SEC-CI-EGRESS` (`TODO.md`, IMP-3 da `AUD-CI-RUNNER`) é um **residual aceito, aberto**, reaberto em 2026-08-04 pela decisão de investigar GPU real no runner (`GH-ONLY-GOLDEN`) -- um device node novo obriga re-rodar o eixo de blast-radius, não só reler o parecer antigo. O container usa a rede `bridge` default do Docker, NAT de saída padrão, **sem allowlist de qualquer tipo**. |

## What would invalidate this decision / O que invalidaria esta decisão

**EN:** This is a risk-accepted decision, not a closed one. It must be revisited, not silently continued, if any of the following happens:

1. **The anti-fork gate (#1) is weakened, disabled, or removed** — `tools/check_workflow_self_hosted_gate.py`'s step is deleted from `ci.yml`, or the script itself stops failing the build on a `pull_request` trigger next to a `self-hosted` job. This is the **only** control with continuous automated verification; losing it removes the entire empirical basis for treating the fork-PR path as closed.
2. **This repository starts receiving real external contribution** — today it is single-author (`ADR-0019`'s own evidence: 698 commits, two git identities, both the líder, zero third-party authors). GitHub's blanket recommendation exists precisely for the "any user can open a pull request" case; a real external contributor changes the trust model this ADR's acceptance rests on, even with the `pull_request` trigger absent (an external contributor with write/PR access could still push a change through review that alters `heavy.yml` itself, or introduce dependencies the sanitizer legs build from source).
3. **`GH-ONLY-GOLDEN`'s GPU spike is approved and `/dev/dri`/`--gpus` is passed into the container** — already flagged in `SEC-CI-EGRESS` as forcing a fresh blast-radius analysis, not a re-read of the old one; a device node is new attack surface this ADR did not evaluate.
4. **A decision is made — either way — on `SEC-CI-EGRESS`** — if the líder invests in an egress allowlist, control #9 moves from absent to present and this ADR's control table should be updated; if the líder decides not to, that is itself worth a dated, explicit re-confirmation rather than an indefinite silent default.
5. **Any of the "enforced by construction, never re-verified" controls (#2, #3, #4, #5, #6, #7, #8 above) is found to have silently drifted** — e.g. a future edit accidentally reintroduces `@v4` on one of `heavy.yml`'s `uses:` lines, or widens `permissions:`. Recommended, not implemented by this ADR (documentation-only per its own restrictions): a future slice could add automated checks for these — the same doctrine `check_workflow_self_hosted_gate.py` already applies to the anti-fork rule.
6. **GitHub's own platform behaviour changes** — e.g. a native isolation mechanism for self-hosted runners on public repos becomes available, or GitHub Actions billing/hosted-runner offerings add a Fedora-class hosted image, removing the practical reason (§ Context, point 2) this runner's Fedora leg exists.

**PT:** Esta é uma decisão de risco aceito, não uma decisão fechada. Precisa ser revisitada, não silenciosamente continuada, se qualquer um dos itens abaixo acontecer:

1. **O gate anti-fork (#1) for enfraquecido, desligado, ou removido** -- o passo do `tools/check_workflow_self_hosted_gate.py` for apagado do `ci.yml`, ou o próprio script parar de falhar o build num gatilho `pull_request` perto de um job `self-hosted`. Este é o **único** controle com verificação automatizada contínua; perdê-lo remove toda a base empírica de tratar o caminho de PR de fork como fechado.
2. **Este repositório começar a receber contribuição externa real** -- hoje é de autor único (a própria evidência do `ADR-0019`: 698 commits, duas identidades git, ambas o líder, zero autores de terceiro). A recomendação geral do GitHub existe precisamente para o caso "qualquer usuário pode abrir um pull request"; um contribuidor externo real muda o modelo de confiança em que a aceitação desta ADR se apoia, mesmo com o gatilho `pull_request` ausente (um contribuidor externo com acesso de escrita/PR ainda poderia empurrar, via review, uma mudança que altere o próprio `heavy.yml`, ou introduzir dependências das quais as pernas de sanitizer buildam do fonte).
3. **O spike de GPU do `GH-ONLY-GOLDEN` for aprovado e `/dev/dri`/`--gpus` passar pro container** -- já sinalizado no `SEC-CI-EGRESS` como forçando uma análise de blast-radius NOVA, não uma releitura da antiga; um device node é superfície de ataque nova que esta ADR não avaliou.
4. **Uma decisão for tomada -- em qualquer sentido -- sobre o `SEC-CI-EGRESS`** -- se o líder investir num allowlist de egress, o controle #9 passa de ausente pra presente e a tabela de controles desta ADR deveria ser atualizada; se o líder decidir não investir, isso por si só merece uma reconfirmação datada e explícita, não um default silencioso indefinido.
5. **Qualquer um dos controles "aplicados por construção, nunca re-verificados" (#2, #3, #4, #5, #6, #7, #8 acima) for achado tendo deriva silenciosa** -- ex.: uma edição futura reintroduzir acidentalmente `@v4` numa das linhas `uses:` do `heavy.yml`, ou ampliar `permissions:`. Recomendado, não implementado por esta ADR (só documentação, pelas próprias restrições dela): uma fatia futura poderia somar checagens automatizadas pra estes -- a mesma doutrina que o `check_workflow_self_hosted_gate.py` já aplica à regra anti-fork.
6. **O próprio comportamento de plataforma do GitHub mudar** -- ex.: um mecanismo nativo de isolamento pra runner self-hosted em repo público ficar disponível, ou as ofertas de runner hospedado/faturamento do GitHub Actions somarem uma imagem hospedada classe Fedora, removendo a razão prática (§ Contexto, ponto 2) pela qual a perna Fedora deste runner existe.

## Options considered / Opções consideradas

- **Chosen / Escolhida -- risco aceito com os controles compensatórios listados, runner self-hosted permanece.** Prós: preserva a perna Fedora dos dois gates (mesma doutrina do `CI-DISTROMATRIX`) e a capacidade latente de máquina estável pro `GLINTFX_PERF_STRICT`; fecha o caminho de ataque especificamente nomeado pelo GitHub (fork PR) via o gate anti-fork automatizado. Contras: continua sendo um desvio nomeado da recomendação geral do GitHub, com vários controles compensatórios sem verificação automática (ver tabela acima).
- **Repositório privado.** Eliminaria o risco pela raiz -- é literalmente o que a política default de grupo de runner do GitHub já pressupõe. Rejeitada: contradiz o objetivo já decidido, separadamente, deste projeto (distribuição ampla e pública, `ADR-0015` framework2d, `ADR-0019` rotação pra Apache-2.0 visando adoção externa). Tornar o repo privado resolveria esta ADR destruindo o motivo de o projeto existir na forma atual.
- **Derrubar o runner self-hosted, confiar só nos equivalentes já hospedados** (o `nightly.yml` já roda o sanitize em Ubuntu/gcc, o `ci.yml` já roda o fonteng em Ubuntu/clang). Prós: elimina 100% da superfície de ataque de runner self-hosted; é a opção "livro-texto conforme". Contras: perde a perna Fedora (cobertura de deriva de distro) e a capacidade latente de máquina estável pra calibração de performance estrita. **Não escolhida hoje, mas nomeada honestamente como disponível** -- se o líder algum dia priorizar conformidade plena sobre a cobertura adicional, esta é a saída mais simples.
- **Grupo de runner restrito, com o repositório continuando público.** Não é de fato uma opção distinta: a própria documentação do GitHub diz que a política default de grupo de runner já restringe a repositório privado -- usar o runner neste repo público já exige a mesma exceção/override que a opção escolhida assume. Dobra-se na opção escolhida.
- **Implementar o allowlist de egress (`SEC-CI-EGRESS`) antes de aceitar o risco.** Rejeitada/adiada por ora: a própria classificação do auditor (razoavelmente adiável, não explorável isoladamente) e a decisão do líder de tratá-la como residual rastreado, não bloqueador -- fica como trabalho futuro nomeado (ver gatilho de revisão #4 acima), não como pré-condição desta ADR.

## Reversibility / Reversibilidade

**EN:** Two-way door on the mechanism, but paired with explicit revisit triggers that make **silent, un-reviewed continuation** the actual risk this ADR guards against, not the difficulty of reversing course. The runner itself can be torn down at any time (`tools/ci/runner_up.sh` stop, `systemd --user` unit disabled) without touching product code; the compensating gate (`check_workflow_self_hosted_gate.py`) is likewise removable with a normal commit, no líder sign-off structurally required by the mechanism itself. What this ADR asks not to be reversible **by default inertia** is the *risk-acceptance decision* — any of the six conditions in "What would invalidate this decision" should trigger an explicit re-confirmation or a new ADR, not a silent "still fine, nobody looked."

**PT:** Porta de mão dupla no mecanismo, mas pareada com gatilhos de revisão explícitos que tornam a **continuação silenciosa e não revisada** o risco real que esta ADR guarda, não a dificuldade de reverter o curso. O próprio runner pode ser derrubado a qualquer momento (`tools/ci/runner_up.sh` stop, unit `systemd --user` desabilitada) sem tocar código de produto; o gate compensatório (`check_workflow_self_hosted_gate.py`) é igualmente removível com um commit normal, sem aval do líder estruturalmente exigido pelo mecanismo em si. O que esta ADR pede que NÃO seja reversível **por inércia default** é a *decisão de aceitar o risco* -- qualquer uma das seis condições em "O que invalidaria esta decisão" deveria disparar uma reconfirmação explícita ou uma ADR nova, não um "continua de boa, ninguém olhou" silencioso.
