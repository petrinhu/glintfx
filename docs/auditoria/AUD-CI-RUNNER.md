# AUD-CI-RUNNER — Self-Hosted CI Runner Security Audit / Auditoria de Segurança do Runner Self-Hosted de CI

- **Date / Data:** 2026-07-29
- **Auditor:** internal-auditor (read-only audit; no product code, no CI file, no `TODO.md` touched; runner not restarted, no workflow dispatched)
- **Scope item / Item da TODO.md:** `AUD-CI-RUNNER` (W18), prerequisite `GH-ONLY-RUNNER`. Origin: revokes the `AUDITORIAS.md` exclusion "Container/k8s/IaC hardening — não faz parte do artefato distribuído (o container só existe no runner de CI)", which went from true to false the day `GH-ONLY-RUNNER` turned that container from a passive build image into a live, persistent, internet-facing execution surface on the lead's own machine.
- **Target / Alvo:** `tools/ci/Containerfile.runner`, `tools/ci/runner_up.sh`, `tools/ci/runner_entrypoint.sh`, `tools/ci/glintfx-heavy-runner.service` (+ the `systemd --user` link installed from it), `.github/workflows/heavy.yml`, `tools/ci/Containerfile.f42` + `tools/ci/build_image.sh` (manual reproduction image, lower stakes — it never registers against GitHub or executes third-party workflow code).
- **Verdict / Veredito:** **CONFORME COM RESSALVAS.** Zero 🔴 CRITICAL findings. Three 🟠 IMPORTANT findings, none exploitable today in isolation (the primary attack path — a fork's `pull_request` reaching the runner — is structurally closed, verified two independent ways), but each removes a layer of defense-in-depth that a public-repo self-hosted runner should have. Three 🟢 COSMETIC findings (hygiene, not security). The live container was inspected running (`docker inspect` + a read-only `docker exec`, no job in flight) and its actual runtime configuration matches what the scripts and comments claim — this report's "PASS" items are runtime-verified, not just read from source.

## Scope / Escopo

**EN:** Per the team-lead's brief: (1) isolation — verify `--cap-drop=ALL`, `--security-opt=no-new-privileges`, non-root user, `--pids-limit`, memory/CPU ceilings **at runtime**, not just as documented intent; (2) credential — the registration token's path from `gh` on the host to the container's `config.sh`, verify it never lands on disk, in `docker inspect`, or persists in the container's environment; (3) the anti-fork boundary on a **public** repository — confirm `pull_request` is absent from `heavy.yml`'s triggers (now and historically) and that no other workflow routes to the `glintfx-heavy` self-hosted label, and judge whether the boundary needs an enforced gate versus a comment; (4) ephemerality — verify structurally (mounts, `--rm`, restart policy) rather than trust the `--ephemeral` flag's name; (5) image — base pin, runner binary pin + checksum, installed surface; (6) blast radius — Docker socket, host `$HOME`, host devices, network mode; (7) secrets in the workflow — `GITHUB_TOKEN` permissions, third-party action pinning. Two things were explicitly **out of scope** and are not re-litigated here: the 8 GiB / 39%-peak memory ceiling (already proven live by `GH-ONLY-RUNNER`, re-confirmed here only structurally via `docker inspect`, not re-measured under load) and whether the job's actual behavior (build correctness, test results) is right — that is `GH-ONLY-RUNNER`'s functional deliverable, this audit is security/compliance only.

**PT:** Conforme o brief do líder: (1) isolamento — verificar `--cap-drop=ALL`, `--security-opt=no-new-privileges`, usuário não-root, `--pids-limit`, tetos de memória/CPU **em tempo de execução**, não só como intenção documentada; (2) credencial — o caminho do token de registro do `gh` no host até o `config.sh` do container, verificar que nunca pousa em disco, em `docker inspect`, nem persiste no ambiente do container; (3) a fronteira anti-fork num repositório **público** — confirmar que `pull_request` está ausente dos gatilhos do `heavy.yml` (hoje e historicamente) e que nenhum outro workflow roteia pro label self-hosted `glintfx-heavy`, e julgar se a fronteira precisa de um gate imposto em vez de um comentário; (4) efemeridade — verificar estruturalmente (mounts, `--rm`, política de restart) em vez de confiar no nome da flag `--ephemeral`; (5) imagem — pin de base, pin+checksum do binário do runner, superfície instalada; (6) blast radius — socket do Docker, `$HOME` do host, dispositivos do host, modo de rede; (7) segredos no workflow — permissões do `GITHUB_TOKEN`, pin de action de terceiro. Duas coisas ficaram explicitamente **fora de escopo** e não são relitigadas aqui: o teto de memória 8 GiB / pico 39% (já provado ao vivo pelo `GH-ONLY-RUNNER`, reconfirmado aqui só estruturalmente via `docker inspect`, não remedido sob carga) e se o comportamento funcional do job (correção de build, resultado de teste) está certo — isso é entregável funcional do `GH-ONLY-RUNNER`, esta auditoria é só segurança/compliance.

**EN:** Read all five in-scope files end-to-end. ## Conclusion / Conclusão

**EN:** The self-hosted runner's core security architecture is sound and, where it makes claims, those claims hold under runtime inspection: capabilities are genuinely zero inside the running container (not just requested), the registration token genuinely never touches disk or `docker inspect`, the container is genuinely mount-less and therefore structurally ephemeral, the pinned runner binary's checksum genuinely matches GitHub's own published hash, and the primary defense — no `pull_request` trigger anywhere near the `self-hosted` label — genuinely holds, verified against the file's entire history and its real run log, not just its current text. The exclusion this item was raised to revoke (`AUDITORIAS.md`'s former "container only exists in CI, out of scope") is correctly revoked: this container now executes code on the lead's own machine on behalf of a public repository, and that is real, audited surface, not speculative IaC hardening. What keeps this from a clean **CONFORME** is that the primary defense is a comment, not a gate (IMP-2); a well-known and specifically-flagged class of self-hosted-runner risk (unpinned third-party actions) is present with no compensating repo policy (IMP-1); and the network layer offers no defense-in-depth should the first two ever be defeated together (IMP-3). None of the three is exploitable in isolation today, and none is a 🔴; the recommended path is IMP-2 first (cheapest, closes the "silent regression" risk entirely), then IMP-1 (mechanical, low-cost pin), with IMP-3 reasonably deferred as an accepted residual until the líder chooses to invest in it. The two runtime-verified positives worth calling out for the external auditor specifically: **zero secrets ever reach this workflow** (`grep secrets\. heavy.yml` → nothing), and **the ambient token is read-only by default** (`permissions: contents: read`, matching the repo's own `default_workflow_permissions`) — even a fully-successful supply-chain compromise via IMP-1 would inherit a token that cannot write to the repository.

**PT:** A arquitetura de segurança central do runner self-hosted é sólida e, onde faz alegações, essas alegações se sustentam sob inspeção em tempo de execução: as capabilities são genuinamente zero dentro do container rodando (não só pedidas), o token de registro genuinamente nunca toca disco nem `docker inspect`, o container é genuinamente sem mount e portanto estruturalmente efêmero, o checksum do binário fixado do runner genuinamente bate com o hash publicado pelo próprio GitHub, e a defesa primária -- nenhum gatilho `pull_request` perto do label `self-hosted` -- genuinamente se sustenta, verificada contra o histórico inteiro do arquivo e o log real de execução, não só o texto atual. A exclusão que este item foi levantado pra revogar (o antigo "container só existe no CI, fora de escopo" do `AUDITORIAS.md`) está corretamente revogada: este container hoje executa código na própria máquina do líder em nome de um repositório público, e isso é superfície real e auditada, não hardening especulativo de IaC. O que impede um **CONFORME** limpo é que a defesa primária é um comentário, não um gate (IMP-2); uma classe bem conhecida e especificamente sinalizada de risco de runner self-hosted (action de terceiro não pinada) está presente sem política compensatória do repo (IMP-1); e a camada de rede não oferece defesa-em-profundidade caso as duas primeiras algum dia sejam derrotadas juntas (IMP-3). Nenhum dos três é explorável isoladamente hoje, e nenhum é 🔴; o caminho recomendado é IMP-2 primeiro (mais barato, fecha inteiramente o risco de "regressão silenciosa"), depois IMP-1 (pin mecânico, baixo custo), com o IMP-3 razoavelmente adiado como residual aceito até o líder optar por investir nele. Os dois pontos positivos verificados em runtime que vale destacar pro auditor externo especificamente: **zero segredo chega a este workflow** (`grep secrets\. heavy.yml` → nada), e **o token ambiente é somente-leitura por padrão** (`permissions: contents: read`, batendo com o próprio `default_workflow_permissions` do repo) -- mesmo um comprometimento de supply-chain via IMP-1 totalmente bem-sucedido herdaria um token incapaz de escrever no repositório.
