# Capability catalog (what glintfx can do, and since when)

> **EN:** A dated, version-pinned index of every glintfx capability -- what it is, the tag it shipped in, the CMake module/flag that gates it (and its default), where to read the full contract, and what it honestly does NOT do. Diátaxis type: **reference**. Audience: an integrator (existing or prospective consumer) deciding whether a capability already exists before building it themselves. Owner: `technical-writer` (glintfx docs); last reviewed **2026-07-29**, against tag `v0.23.0`.
> **PT:** Índice datado e pinado-por-versão de toda capacidade da glintfx -- o que é, a tag em que chegou, o módulo/flag do CMake que a gateia (e o default dela), onde ler o contrato completo, e o que ela honestamente NÃO faz. Tipo Diátaxis: **reference**. Audiência: um integrador (consumidor atual ou futuro) decidindo se uma capacidade já existe antes de construí-la de novo. Owner: `technical-writer` (docs da glintfx); última revisão **2026-07-29**, contra a tag `v0.23.0`.

**EN:** This catalog exists because of a real distribution failure, not a code gap: a consumer (GusWorld) kept maintaining its own audio and gamepad backends for weeks after both had shipped, with the flags `ON` by default, inside the exact pinned version it was already consuming. The code was there; nobody had told them in a form they'd see. If you are wiring a capability into a host and don't see it below, it genuinely does not exist yet -- open an INBOX item instead of building around it silently.

Se você está conectando uma capacidade num host e não a vê abaixo, ela genuinamente ainda não existe -- abra um item na INBOX em vez de contornar em silêncio.

## English

### How to read this table

- **Since:** the exact `vX.Y.Z` tag the capability first shipped in (verified against `CHANGELOG.md` section boundaries and `git tag -l`, not guessed from prose).
- **Module / flag (default):** the `GLINTFX_MODULE_*` CMake option that compiles the capability in or out, and its default in `glintfx/CMakeLists.txt` as of `v0.23.0`. "n/a" means there is no dedicated flag -- the capability is part of the always-compiled core surface.
- **Doc:** where the full contract lives. A capability with no dedicated `docs/*.md` file is marked explicitly -- that is a real gap, not an oversight in this catalog (see "Confirmed gaps" below).
- **Limitations:** the honest ceiling, taken from the shipping CHANGELOG entry and the linked doc, not softened.

| **Image encode** (`encode_image_memory()`/`encode_image_file()`, `glintfx::ImageFormat`) -- PNG/JPG/PPM/BMP/TGA/HDR/QOI, to disk OR an owned in-memory buffer | **`Unreleased`** (`IMG-ENCODE`, W21) -- not yet tagged, same update-at-release discipline as the `FW-LOG`/`FW-CLOCK` rows above | rides `GLINTFX_MODULE_IMAGE` (same forced-ON reservation as Image decode's own row, no separate flag) | [`glintfx/include/glintfx/image.hpp`](../glintfx/include/glintfx/image.hpp) (no dedicated `docs/*.md` section yet -- same accepted gap class as `i18n`/`log`/`clock`, see "Confirmed gaps" below) | **Exactly SEVEN formats and no others, a declared ceiling, not a temporary gap:** no metadata/EXIF of any kind, no animation (no APNG/GIF), no quality knob beyond `EncodeImageOptions::jpg_quality` (JPG only -- the one format where "quality" is a cheap, meaningful, single number; PNG's own zlib compression LEVEL is deliberately NOT exposed, it trades size/CPU with zero visual effect since PNG is lossless either way). **JPG** has no alpha channel and is lossy (DCT/chroma-subsampling) -- wrong choice for a sprite/UI asset needing exact colour or transparency. **HDR** is a DECLARED DOWNGRADE: this module's only input is 8-bit RGBA8, so HDR output is always a straight `/255.0f` conversion of that -- no real extended dynamic range is ever produced (nothing in glintfx today produces a float-valued pixel buffer), useful only as a Radiance/`.hdr` file-format CONTAINER for a downstream tool that reads it. **QOI** is lossless and fast but read by almost no external tool -- right for this library's own internal round-trip/cache use, wrong for interchange; **QOI DECODE does not exist** (encode only), tracked as a future INBOX item if a real need to read QOI back in is ever measured. Input is straight (non-premultiplied) RGBA8, `width * height * 4` bytes, top-left origin, y-down -- the SAME layout Image decode's own `DecodedImagePixels` uses, so a decode -> re-encode round trip needs zero conversion. `kMaxImageEncodeBytes` (64 MiB, `image_encode.cpp`) caps the RAW input pixel buffer -- a 4K UHD RGBA8 frame (~33 MiB) fits with headroom, an 8K capture (~133 MiB) does not (declared, not an oversight) |

The consumer-facing point of these rows: **the ceiling below is a promise, not a placeholder.** Each was written into this catalog in the SAME commit that shipped the capability (`FW-LOG`, `FW-CLOCK`), before any host had a chance to ask for more -- see "Process: announce, don't just ship" below for why that ordering matters.

| :--- | :--- | :--- | :--- | :--- |

| **`glintfx::monotonic_now_ns()`** -- monotonic nanosecond clock, a stateless, thread-safe, thin wrapper over `std::chrono::steady_clock`, the `SDL_GetTicksNS()` equivalent for a fixed-step accumulator/duration-measurement/animation-timing host | **`Unreleased`** (`FW-CLOCK`, W20) -- not yet tagged; same update-at-release discipline as the `FW-LOG` row above | n/a -- core, ZERO dependency of any kind (not even `RmlUi::Core`), always compiled, same independence class as `version()`/`log()` | [`glintfx/include/glintfx/clock.hpp`](../glintfx/include/glintfx/clock.hpp) (no dedicated `docs/clock.md` yet -- same accepted gap class as `i18n`/`log`, see "Confirmed gaps" below) | **Deliberately a single function, nothing more -- the honest verdict is stated in the header itself:** if the only property a caller needs is "a clock that never goes backwards", `std::chrono::steady_clock` already provides that with zero wrapper needed (the requesting consumer said so itself); the measured value this module adds is narrower -- a fixed-nanosecond return contract regardless of platform `steady_clock::period`, a zero-diff migration shape matching `SDL_GetTicksNS()`'s exact signature, and an integer (not `std::chrono` template) ABI shape. No timer/interval/scheduling API, no wall-clock/calendar function, no per-thread or per-subsystem clock instance -- one process-wide monotonic reading, on purpose, per the same "measured need, not speculative surface" discipline as `FW-LOG` above (17 `SDL_GetTicksNS()` call sites measured, all doing exactly this and nothing more) |

### Confirmed gaps found while building this catalog

- **`docs/i18n.md` does not exist.** `i18n` (`v0.13.0`) is the only atomized module without a dedicated reference doc -- `audio.md`, `gamepad.md`, and `draw2d.md` all exist, `i18n` does not. Today the only source is the bilingual doc-comment header (`glintfx/include/glintfx/i18n.hpp`) and the `CHANGELOG.md` entry. Recommend a follow-up item (not filed here, per this task's scope -- report to the team lead).
- **Color emoji (COLRv0, `v0.17.0`) has no CHANGELOG cross-reference into `docs/effects.md`'s "Note: COLRv0 colour emoji" section** -- the doc section itself is complete and accurate, it is simply not linked FROM the CHANGELOG entry (a reader following the release notes has to already know to look in `effects.md`). Minor, not a content gap.
- **`README.md`'s "Roadmap and vision" section is stale against `CHANGELOG.md`.** Its prose narrative stops at `v0.18.0` ("Current release: v0.18.0") while the repository is tagged `v0.23.0` -- five releases (`v0.19.0` HOSTIN/LOGTHR, `v0.20.0`-`v0.23.0` the entire Draw2D arc) are undescribed there, even though the version badge at the top of the file correctly reads `0.23.0`. This is very likely a contributor to the same distribution problem this catalog fixes, and is now largely superseded by this catalog and its Draw2D/emoji/HOSTIN rows above -- flagged here for the team lead's judgment on whether to also refresh that prose (out of this task's explicit scope: create-and-link, not rewrite the roadmap).
- **No divergences found between `CHANGELOG.md`'s stated tag, `git tag -l`, and `glintfx/CMakeLists.txt`'s actual `option()` defaults** for any capability listed above -- every "Since" and every default in this catalog was verified against the CMake source and the exact CHANGELOG section boundary (by line-range, not by searching for a version string in prose), not inferred.

### Process: announce, don't just ship

**The habit that was missing, and the one this catalog exists to install:** at the close of every release that adds or changes a capability, the release announcement to consumer(s) (today: GusWorld, via the bus at `gusworld_ia_autocomm/inbox/gusworld/`) must **name the capability by benefit** ("audio playback is now built in, delete your own miniaudio integration"), not just cite the CHANGELOG entry ID. A consumer scanning 57 backlogged bus messages should not have to reverse-engineer `AUDIO-F2` into "oh, we don't need our own audio code anymore" -- say it plainly, once, at the moment it becomes true. Update this catalog (`docs/capabilities.md`) in the same commit that lands a new module or a materially new capability -- treat a missing row here as equivalent to a missing test.

Input é RGBA8 straight (não-premultiplicado), `width * height * 4` bytes, origem superior-esquerda, y pra baixo -- o MESMO layout que o próprio `DecodedImagePixels` do Decode de imagem usa, então um round trip decode -> re-encode não precisa de conversão nenhuma. `kMaxImageEncodeBytes` (64 MiB, `image_encode.cpp`) limita o buffer de pixel de input CRU -- um frame 4K UHD RGBA8 (~33 MiB) cabe com folga, uma captura 8K (~133 MiB) não cabe (declarado, não um descuido) |

### Lacunas confirmadas achadas ao construir este catálogo

- **`docs/i18n.md` não existe.** O `i18n` (`v0.13.0`) é o único módulo atomizado sem doc de referência dedicado -- `audio.md`, `gamepad.md` e `draw2d.md` todos existem, `i18n` não. Hoje a única fonte é o header com doc-comment bilíngue (`glintfx/include/glintfx/i18n.hpp`) e a entrada do `CHANGELOG.md`. Recomendo um item de follow-up (não aberto aqui, fora do escopo desta tarefa -- reportado ao líder do time).
- **O emoji colorido (COLRv0, `v0.17.0`) não tem cross-referência do CHANGELOG pra seção "Nota: emoji colorido COLRv0" do `docs/effects.md`** -- a própria seção do doc está completa e correta, ela só não é linkada A PARTIR da entrada do CHANGELOG (um leitor seguindo as release notes já precisa saber que deve procurar em `effects.md`). Menor, não é lacuna de conteúdo.
- **A seção "Roadmap and vision"/"Roadmap e visão" do `README.md` está defasada contra o `CHANGELOG.md`.** A narrativa em prosa dela para na `v0.18.0` ("Current release: v0.18.0") enquanto o repositório está taggeado `v0.23.0` -- cinco releases (`v0.19.0` HOSTIN/LOGTHR, `v0.20.0`-`v0.23.0` o arco inteiro do Draw2D) ficam sem descrição ali, mesmo com o badge de versão no topo do arquivo lendo corretamente `0.23.0`. Isto muito provavelmente contribuiu pro mesmo problema de distribuição que este catálogo conserta, e agora fica em grande parte suprido por este catálogo e pelas linhas de Draw2D/emoji/HOSTIN acima -- sinalizado aqui pro julgamento do líder do time sobre também refrescar aquela prosa (fora do escopo explícito desta tarefa: criar-e-linkar, não reescrever o roadmap).
- **Nenhuma divergência achada entre a tag declarada no `CHANGELOG.md`, o `git tag -l`, e os defaults reais de `option()` do `glintfx/CMakeLists.txt`** para nenhuma capacidade listada acima -- todo "Desde" e todo default deste catálogo foi verificado contra o source do CMake e a fronteira exata de seção do CHANGELOG (por faixa de linha, não por busca de string de versão na prosa), não inferido.

### Processo: anuncie, não só lance

**O hábito que faltava, e o que este catálogo existe para instalar:** ao fechar toda release que adiciona ou muda uma capacidade, o anúncio de release ao(s) consumidor(es) (hoje: GusWorld, via o bus em `gusworld_ia_autocomm/inbox/gusworld/`) precisa **nomear a capacidade pelo benefício** ("reprodução de áudio agora vem embutida, apague a própria integração miniaudio"), não só citar o ID da entrada do CHANGELOG. Um consumidor varrendo 57 mensagens acumuladas do bus não deveria ter que fazer engenharia reversa de `AUDIO-F2` pra "ah, não precisamos mais do nosso próprio código de áudio" -- diga isso de forma direta, uma vez, no momento em que vira verdade. Atualize este catálogo (`docs/capabilities.md`) no MESMO commit que pousa um módulo novo ou uma capacidade materialmente nova -- trate uma linha faltando aqui como equivalente a um teste faltando.
