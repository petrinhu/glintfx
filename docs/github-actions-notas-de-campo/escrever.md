## 1. Gatilhos / Triggers (`on:`)

### 1.1 Sintaxe geral / General syntax

**EN:** `on:` accepts a single event (`on: push`), a list (`on: [push, fork]`), or a map with per-event configuration. If you specify activity types or filters for an event, you must configure each event as a map key with a colon, even events with no configuration. If multiple trigger events occur at the same time, multiple workflow runs are triggered independently.

**PT:** `on:` aceita um evento único (`on: push`), uma lista (`on: [push, fork]`) ou um mapa com configuração por evento. Se você especifica tipos de atividade ou filtros para um evento, precisa configurar cada evento como chave de mapa com dois-pontos, mesmo os eventos sem configuração. Se vários eventos de gatilho ocorrerem ao mesmo tempo, várias execuções são disparadas independentemente.

### 1.2 Filtros de `branches`/`tags`/`paths`

**EN:** `branches`/`branches-ignore` and `tags`/`tags-ignore` are mutually exclusive per event (can't use both for the same event); to include-and-exclude in one filter, use `branches` with a `!` prefix for the excluded patterns — order matters: a negative pattern after a positive one excludes; a positive pattern after a negative one re-includes. If you set `branches`/`branches-ignore` **and** `paths`/`paths-ignore`, the workflow only runs when **both** are satisfied (they're ANDed, not ORed). `paths` filters are **not evaluated on tag pushes**.

Git-diff mechanics behind `paths`: GitHub computes a two-dot diff for pushes to existing branches, a two-dot diff against the parent of the deepest pushed commit for pushes to new branches, and a three-dot diff for pull requests. Three hard limits:
- A push with **more than 1,000 commits** always runs the workflow (the diff isn't computed).
- If diff generation times out, the workflow always runs.
- If the diff has **more than 3,000 files** and the paths your filter matches aren't among the first 3,000 returned, the **workflow does not run**.

**PT:** `branches`/`branches-ignore` e `tags`/`tags-ignore` são mutuamente exclusivos por evento (não dá pra usar os dois pro mesmo evento); pra incluir-e-excluir num só filtro, use `branches` com prefixo `!` nos padrões excluídos — a ordem importa: um padrão negativo depois de um positivo exclui; um positivo depois de um negativo reinclui. Se você define `branches`/`branches-ignore` **e** `paths`/`paths-ignore`, o fluxo só roda quando **os dois** forem satisfeitos (é E lógico, não OU). Filtros de `paths` **não são avaliados em push de tag**.

Mecânica do git-diff atrás de `paths`: o GitHub calcula um diff de dois pontos para push em branch existente, um diff de dois pontos contra o pai do commit mais profundo do push para branch nova, e um diff de três pontos para pull request. Três limites duros:
- Push com **mais de 1.000 commits** sempre roda o fluxo (o diff nem é calculado).
- Se a geração do diff der timeout, o fluxo sempre roda.
- Se o diff tiver **mais de 3.000 arquivos** e os caminhos que seu filtro casa não estiverem entre os primeiros 3.000 retornados, o **fluxo não roda**.

**EN — tie to our practice:** all 6 of our workflows use `paths:` filters scoped to the tree they build (`glintfx/**`, `src/**`+`include/**`+`tests/**`+`tools/**`+`Makefile` for `core-ci.yml`, narrower per-file lists for `windows-atoms.yml`). None of us has ever come close to 1,000 commits in one push or 3,000 changed files, so these limits are theoretical for us today — but they are the kind of thing that turns a `paths:`-filtered workflow silently into an always-run workflow on a giant merge or a repo-wide reformat commit. Worth remembering before a large mechanical rename.

**PT — amarração com a nossa prática:** os nossos 6 fluxos usam `paths:` recortado pra árvore que cada um builda (`glintfx/**`, `src/**`+`include/**`+`tests/**`+`tools/**`+`Makefile` no `core-ci.yml`, listas mais estreitas por arquivo no `windows-atoms.yml`). Nunca chegamos perto de 1.000 commits num push ou 3.000 arquivos alterados, então esses limites são teóricos pra nós hoje — mas são o tipo de coisa que transforma silenciosamente um fluxo filtrado por `paths:` num fluxo que sempre roda, num merge gigante ou num commit de reformatação do repo inteiro. Vale lembrar antes de um rename mecânico grande.

### 1.3 `workflow_dispatch` — o gatilho manual, e a amarração com `CI-DISPATCH-MANUAL`

**EN:** `workflow_dispatch` lets you trigger a workflow manually via the GitHub API, GitHub CLI, or the web UI. You can define `inputs` with `description`, `required`, `default`, and `type` (`choice` with an `options` list, `boolean`, `string`, `environment`). Inputs are available both in `inputs.<name>` (preserves booleans as booleans; `choice` resolves to a single selected string) and in `github.event.inputs.<name>` (everything stringified). Hard limits: **max 25 top-level input properties**, **max 65,535 characters** of input content.

**The line that explains the whole incident, quoted exactly from the reference page (`events-that-trigger-workflows`):** *"Esse gatilho só recebe eventos quando o arquivo de fluxo de trabalho está na ramificação padrão"* — this trigger only receives events when the workflow file is on the default branch. The same sentence, verbatim, is repeated for `schedule`, `repository_dispatch`, `status`, `watch`, `workflow_call`, and `workflow_run` too: **all of them require the trigger to already exist, committed, on the default branch before they can fire.** `trigger-a-workflow` adds the corollary explicitly for `workflow_dispatch`: it "só recebe eventos quando o arquivo de fluxo de trabalho está na ramificação padrão."

**This is the mechanism behind our `CI-DISPATCH-MANUAL` incident, not just a coincidence.** During the ~4h GitHub Actions outage on 2026-08-06, `push` events stopped creating workflow runs at all, while `gh workflow run <file> --ref main` kept working — but only for `heavy.yml` and `distro-matrix.yml`, which already had `workflow_dispatch:` committed to `main`. `ci.yml` (the release gate), `core-ci.yml`, and `windows-atoms.yml` returned `HTTP 422: Workflow does not have 'workflow_dispatch' trigger` — the manual escape hatch simply didn't exist for the three workflows that mattered most, and it couldn't be added retroactively for a run that needed to happen *now*: per the doc's own rule, adding `workflow_dispatch:` only takes effect once that change is itself on the default branch. The fix (`75ad1ba`, one `workflow_dispatch:` line added to each of the three `on:` blocks) had to be **pushed and merged to `main` first**, and only then could the three workflows be dispatched manually — which is exactly what happened (verified after push: all three created `in_progress` runs, no more `422`).

**The transferable rule the documentation itself states, and which now has a name for us:** a workflow's manual-dispatch capability is **not** something you can bolt on at the moment of need. It has to be present on `main` *in advance*, the same way a fire exit has to exist before the fire, not be built during it. **Every workflow that might ever need to run outside its normal trigger — which in practice means every workflow — should carry `workflow_dispatch:` from day one**, even with zero `inputs`.

**PT:** `workflow_dispatch` permite disparar um fluxo manualmente via API do GitHub, GitHub CLI ou a interface web. Você define `inputs` com `description`, `required`, `default` e `type` (`choice` com lista `options`, `boolean`, `string`, `environment`). As entradas ficam disponíveis tanto em `inputs.<nome>` (preserva booliano como booliano; `choice` resolve pra uma única string selecionada) quanto em `github.event.inputs.<nome>` (tudo virando string). Limites duros: **máximo 25 propriedades de nível superior** em `inputs`, **máximo 65.535 caracteres** de conteúdo.

**A frase que explica o incidente inteiro, citada exatamente da página de referência (`events-that-trigger-workflows`):** *"Esse gatilho só recebe eventos quando o arquivo de fluxo de trabalho está na ramificação padrão"*. A mesma frase, palavra por palavra, se repete para `schedule`, `repository_dispatch`, `status`, `watch`, `workflow_call` e `workflow_run` também: **todos eles exigem que o gatilho já exista, commitado, no branch padrão antes de poder disparar.** A página `trigger-a-workflow` reforça o corolário explícito para `workflow_dispatch`: ele "só recebe eventos quando o arquivo de fluxo de trabalho está na ramificação padrão."

**Este é o mecanismo por trás do nosso incidente `CI-DISPATCH-MANUAL`, não uma coincidência.** Durante a pane de ~4h do GitHub Actions em 2026-08-06, eventos de `push` pararam de criar execução nenhuma, enquanto `gh workflow run <arquivo> --ref main` continuou funcionando — mas só para `heavy.yml` e `distro-matrix.yml`, que já tinham `workflow_dispatch:` commitado na `main`. `ci.yml` (o gate de release), `core-ci.yml` e `windows-atoms.yml` devolveram `HTTP 422: Workflow does not have 'workflow_dispatch' trigger` — a válvula de escape manual simplesmente não existia para os três fluxos que mais importavam, e não dava pra acrescentá-la retroativamente pra uma execução que precisava acontecer *agora*: pela regra da própria documentação, adicionar `workflow_dispatch:` só faz efeito depois que essa mudança em si está no branch padrão. O conserto (`75ad1ba`, uma linha `workflow_dispatch:` acrescentada em cada um dos três blocos `on:`) teve de ser **pusheado e mesclado na `main` primeiro**, e só então os três puderam ser disparados manualmente — que foi exatamente o que aconteceu (verificado depois do push: os três criaram execuções `in_progress`, sem mais `422`).

**A regra transferível que a própria documentação afirma, e que agora tem nome pra nós:** a capacidade de disparo manual de um fluxo **não** é algo que se acopla no momento da necessidade. Ela tem que estar presente na `main` *com antecedência*, do mesmo jeito que uma saída de incêndio precisa existir antes do incêndio, não ser construída durante ele. **Todo fluxo que algum dia possa precisar rodar fora do gatilho normal — o que na prática é todo fluxo — deveria carregar `workflow_dispatch:` desde o dia zero**, mesmo com zero `inputs`.

### 1.4 `schedule` (cron)

**EN:** POSIX cron syntax, 5 fields (minute, hour, day-of-month, month, day-of-week), operators `* , - /`. Default timezone UTC; an IANA timezone string can be set for the schedule. **Non-standard syntax is not supported** (`@yearly`, `@monthly`, `@weekly`, `@daily`, `@hourly`, `@reboot`). **Shortest interval is every 5 minutes.** *"O evento `schedule` pode ser atrasado durante períodos de cargas altas de execuções... Os tempos de carregamento altos incluem o início de cada hora."* — this is the documented reason our `nightly.yml` runs at `17 3 * * *` (03:17 UTC) instead of a round hour, with the exact rationale spelled out in the workflow's own comment (off-peak, avoids the thundering herd at `:00`). Scheduled workflows only run on the default branch and are **automatically disabled after 60 days of no repository activity** on public repos (matches our own convention of watching `gh run list` — a schedule going silent for 60 days on a quiet repo is a self-inflicted, silent disable, not a platform bug).

**PT:** Sintaxe cron POSIX, 5 campos (minuto, hora, dia-do-mês, mês, dia-da-semana), operadores `* , - /`. Fuso padrão UTC; pode-se definir fuso IANA para o agendamento. **Sintaxe não-padrão não é suportada** (`@yearly`, `@monthly`, `@weekly`, `@daily`, `@hourly`, `@reboot`). **Intervalo mais curto é a cada 5 minutos.** *"O evento `schedule` pode ser atrasado durante períodos de cargas altas... Os tempos de carregamento altos incluem o início de cada hora."* — esta é a razão documentada de o nosso `nightly.yml` rodar às `17 3 * * *` (03:17 UTC) em vez de uma hora redonda, com a mesma racional já escrita no comentário do próprio fluxo (fora de pico, evita a debandada às `:00`). Fluxos agendados só rodam no branch padrão e são **desabilitados automaticamente após 60 dias sem atividade** no repositório público (bate com a nossa própria convenção de vigiar `gh run list` — um schedule que emudece por 60 dias num repo quieto é um desligamento silencioso auto-infligido, não um bug da plataforma).

### 1.5 `repository_dispatch`

**EN:** Fired via REST API for activity outside GitHub; requires an `event_type` (max 100 chars) and optional `client_payload` (max 10 top-level properties, max 65,535 characters), available under `github.event.client_payload`. Not used by any of our 6 workflows today — **não confirmado como necessário** for anything in our roadmap; noted here for completeness.

**PT:** Disparado via API REST para atividade fora do GitHub; exige `event_type` (máx. 100 caracteres) e `client_payload` opcional (máx. 10 propriedades de nível superior, máx. 65.535 caracteres), disponível em `github.event.client_payload`. Não usado por nenhum dos nossos 6 fluxos hoje — **não confirmado como necessário** para nada no nosso roadmap; registrado aqui por completude.

### 1.6 `GITHUB_TOKEN` não redispara fluxo (proteção anti-recursão)

**EN:** Events triggered by the repo's own `GITHUB_TOKEN` do **not** create a new workflow run, with two exceptions: `workflow_dispatch`/`repository_dispatch` always create runs, and `pull_request` with `opened`/`synchronize`/`reopened` created via `GITHUB_TOKEN` create runs in an **"aprovação-obrigatória"** state requiring a write-access user to approve. This is a deliberate anti-recursion guard: if a workflow run pushes a commit using `GITHUB_TOKEN`, that push does **not** trigger a new run even if the repo has a `push`-triggered workflow. To intentionally trigger a downstream workflow from inside a run, use a GitHub App installation token or a personal access token instead of `GITHUB_TOKEN`.

**PT:** Eventos disparados pelo próprio `GITHUB_TOKEN` do repositório **não** criam nova execução, com duas exceções: `workflow_dispatch`/`repository_dispatch` sempre criam execuções, e `pull_request` com `opened`/`synchronize`/`reopened` criado via `GITHUB_TOKEN` cria execuções em estado **"aprovação-obrigatória"**, exigindo aprovação de um usuário com acesso de escrita. É uma guarda anti-recursão deliberada: se uma execução faz push de um commit usando `GITHUB_TOKEN`, esse push **não** dispara nova execução mesmo que o repo tenha um fluxo disparado por `push`. Pra disparar intencionalmente um fluxo downstream de dentro de uma execução, use um token de instalação de GitHub App ou um personal access token em vez de `GITHUB_TOKEN`.

### 1.7 Concorrência (`concurrency:`)

**EN:** `concurrency` (workflow-level or `jobs.<job_id>.concurrency`) ensures only one job/workflow run in a given concurrency group runs at a time; a queued run in the same group goes `pending`. By default a new run cancels any existing `pending` run in the same group (does **not** cancel an in-progress one unless `cancel-in-progress: true`). `queue: max` (up to 100 queued at once) is **mutually exclusive** with `cancel-in-progress: true` — combining them is a validation error. Group names are case-insensitive. Allowed expression contexts inside the group key: `github`, `inputs`, `vars`, `needs`, `strategy`, `matrix`.

**PT:** `concurrency` (nível de fluxo ou `jobs.<job_id>.concurrency`) garante que só um job/execução do mesmo grupo de simultaneidade rode por vez; uma execução enfileirada no mesmo grupo fica `pending`. Por padrão, uma nova execução cancela qualquer execução `pending` existente no mesmo grupo (**não** cancela uma em andamento, a menos que `cancel-in-progress: true`). `queue: max` (até 100 enfileiradas por vez) é **mutuamente exclusivo** com `cancel-in-progress: true` — combinar os dois é erro de validação. Nome de grupo não diferencia maiúsculas/minúsculas. Contextos de expressão permitidos na chave do grupo: `github`, `inputs`, `vars`, `needs`, `strategy`, `matrix`.

**EN — our practice:** `heavy.yml` already uses exactly the documented pattern for a self-hosted, resource-constrained runner: `concurrency: { group: heavy-${{ github.ref }}, cancel-in-progress: true }`. This matches the doc's "Example: Using concurrency to cancel any in-progress job or run" pattern precisely, and given the container runner's declared ceiling (8 GiB / 4 CPUs, no swap), it's the correct choice — a second `heavy` run queuing behind a first one instead of cancelling it would risk two concurrent ASan builds fighting over the same memory ceiling.

**PT — nossa prática:** o `heavy.yml` já usa exatamente o padrão documentado para um runner self-hosted com recurso limitado: `concurrency: { group: heavy-${{ github.ref }}, cancel-in-progress: true }`. Bate precisamente com o padrão "Exemplo: Usar a concorrência para cancelar qualquer trabalho em andamento" da doc, e dado o teto declarado do runner conteinerizado (8 GiB / 4 CPUs, sem swap), é a escolha certa — uma segunda execução de `heavy` enfileirando atrás da primeira em vez de cancelá-la arriscaria dois builds ASan concorrentes brigando pelo mesmo teto de memória.

## 2. Estrutura: jobs, steps, needs, if, continue-on-error, outputs

### 2.1 `jobs.<job_id>`

**EN:** `<job_id>` is a unique map key, must start with a letter or `_`, and contain only alphanumerics, `-`, or `_`. `jobs.<job_id>.name` sets the display name.

**PT:** `<job_id>` é uma chave de mapa única, precisa começar com letra ou `_`, e conter só alfanuméricos, `-` ou `_`. `jobs.<job_id>.name` define o nome exibido.

### 2.2 `needs` — dependência e propagação de falha

**EN:** `jobs.<job_id>.needs` (string or array) lists jobs that must complete successfully before this one runs. Quoted directly: *"Se houver falha em um trabalho ou ele for ignorado, todos os trabalhos que dependem dele serão ignorados, a menos que os trabalhos usem uma expressão condicional que faça o trabalho continuar. Se uma execução contiver uma série de trabalhos que precisem uns dos outros, uma falha ou omissão se aplicará a todos os trabalhos na cadeia de dependência do ponto de falha ou omissão em diante."* To run a downstream job regardless of upstream success, use `if: ${{ always() }}` at the job level.

**PT:** `jobs.<job_id>.needs` (string ou array) lista jobs que precisam terminar com sucesso antes deste rodar. Citação direta: *"Se houver falha em um trabalho ou ele for ignorado, todos os trabalhos que dependem dele serão ignorados, a menos que os trabalhos usem uma expressão condicional que faça o trabalho continuar. Se uma execução contiver uma série de trabalhos que precisem uns dos outros, uma falha ou omissão se aplicará a todos os trabalhos na cadeia de dependência do ponto de falha ou omissão em diante."* Pra rodar um job downstream independente do sucesso do upstream, use `if: ${{ always() }}` no nível de job.

**EN — measured, not assumed:** none of our 6 workflows use `needs:` anywhere (`grep -n "needs:" *.yml` returns zero matches). Every job in every one of our workflows is independent — they fan out in parallel and the workflow's own pass/fail is the aggregate of all its jobs, not a hand-built dependency chain. That's a legitimate design (our jobs don't produce artifacts one another consumes), but it also means the `needs`-driven "skip the whole downstream chain on failure" behavior described above has never been exercised in this repo. If a future job legitimately needs another job's output (matrix built once, consumed by several), this is the mechanism, and it comes with the `outputs` machinery in §2.4.

**PT — medido, não presumido:** nenhum dos nossos 6 fluxos usa `needs:` em lugar nenhum (`grep -n "needs:" *.yml` devolve zero ocorrências). Todo job em todo fluxo nosso é independente — eles se espalham em paralelo e o resultado do fluxo é o agregado de todos os jobs, não uma cadeia de dependência construída à mão. É um desenho legítimo (nossos jobs não produzem artefato que outro consome), mas também significa que o comportamento "pula a cadeia downstream inteira na falha", descrito acima, nunca foi exercitado neste repo. Se um job futuro precisar legitimamente da saída de outro (matriz construída uma vez, consumida por vários), é este o mecanismo, e ele vem junto com a maquinaria de `outputs` do §2.4.

### 2.3 `if:` — condicional em job e step

**EN:** `jobs.<job_id>.if` prevents a job from running unless a condition is met; any supported context/expression works. Quoted: *"Um trabalho que é ignorado relatará o respectivo status como 'Success'. Ele não impedirá a mesclagem de uma solicitação de pull, mesmo que seja uma verificação necessária."* — a skipped required check still reports green. Debugging: view "job condition expression logs" in the run UI to see why a job ran or was skipped unexpectedly.

**PT:** `jobs.<job_id>.if` impede a execução do job a menos que a condição seja atendida; qualquer contexto/expressão suportado funciona. Citação: *"Um trabalho que é ignorado relatará o respectivo status como 'Success'. Ele não impedirá a mesclagem de uma solicitação de pull, mesmo que seja uma verificação necessária."* — um required check ignorado ainda reporta verde. Depuração: ver "logs de expressão de condição de tarefa" na UI da execução pra entender por que um job rodou ou foi ignorado inesperadamente.

### 2.4 `continue-on-error` e `fail-fast`

**EN:** `jobs.<job_id>.continue-on-error` (job level) or `steps[*].continue-on-error` (step level) lets a job/step fail without failing the run or blocking other jobs. It composes with `strategy.fail-fast`: with `fail-fast: true`, any job with `continue-on-error: false` that fails cancels all pending/in-progress jobs in the matrix; a job with `continue-on-error: true` that fails does **not** affect the others. Documentation quote: *"`fail-fast` e `continue-on-error` podem ser usados juntos."*

**PT:** `jobs.<job_id>.continue-on-error` (nível de job) ou `steps[*].continue-on-error` (nível de step) deixa um job/step falhar sem falhar a execução nem bloquear outros jobs. Compõe com `strategy.fail-fast`: com `fail-fast: true`, qualquer job com `continue-on-error: false` que falhar cancela todos os jobs pendentes/em andamento da matriz; um job com `continue-on-error: true` que falha **não** afeta os outros. Citação da documentação: *"`fail-fast` e `continue-on-error` podem ser usados juntos."*

**EN — our practice, and its tie to `CI-TIDY-CRASH`:** `continue-on-error` is not used anywhere in our 6 workflows today — it appears exactly twice, both as comments describing a *contingency*, never applied. In `ci.yml` (job `windows-msvc-build`), a comment reads: *"Se o vcpkg... se mostrar flaky na prática, a resposta é estreitar o escopo mais (ex.: `continue-on-error: true` na perna afetada enquanto se investiga) em vez de derrubar o gate"* — the project already treats `continue-on-error` as a deliberate, narrow, documented escape hatch, never a default, which matches this doc's model of it (a scoped exception, not a blanket ignore-failures switch).

This is also the right place to name the mechanism behind `CI-TIDY-CRASH`: `clang-tidy` was invoked once, in batch, across 51 files. When it received a SIGSEGV (**exit 139**, the tool itself dying — distinct from **exit 1**, a real lint violation), the batch step failed as a unit and nothing distinguished "51 files clean" from "5 files never analyzed and 46 clean" — the step's pass/fail is a single bit, and neither `if:`/`always()` nor `continue-on-error` (which govern whether a step's failure blocks *other* steps/jobs) tell you anything about **partial completion within one step**. Nothing in the `on:`/`jobs`/`continue-on-error` model documented here rescues you from an aggregate step swallowing per-unit failure — the fix the project applied (loop file-by-file, each iteration its own accounted-for outcome, printing `encontrados`/`analisados`/`falharam` even when zero, and treating exit 139 differently from exit 1) is exactly the granularity `continue-on-error` operates at (step/job), just pushed down one level, by hand, into the step's own shell loop. The documentation's job/step model gives you a pass/fail *per step*; it does not give you one *per file inside a step that batches 51 of them* — that has to be built by the workflow author, which is what the fix did.

**PT — nossa prática, e a amarração com o `CI-TIDY-CRASH`:** `continue-on-error` não é usado em lugar nenhum dos nossos 6 fluxos hoje — aparece exatamente duas vezes, as duas como comentário descrevendo uma *contingência*, nunca aplicado. No `ci.yml` (job `windows-msvc-build`), um comentário diz: *"Se o vcpkg... se mostrar flaky na prática, a resposta é estreitar o escopo mais (ex.: `continue-on-error: true` na perna afetada enquanto se investiga) em vez de derrubar o gate"* — o projeto já trata `continue-on-error` como uma válvula de escape deliberada, estreita e documentada, nunca um padrão, o que bate com o modelo que a doc descreve (uma exceção com escopo, não um botão geral de ignorar falhas).

Este também é o lugar certo pra nomear o mecanismo por trás do `CI-TIDY-CRASH`: o `clang-tidy` era invocado uma vez, em lote, contra 51 arquivos. Quando ele recebia um SIGSEGV (**exit 139**, a própria ferramenta morrendo — distinto de **exit 1**, uma violação de lint real), o step em lote falhava como uma unidade e nada distinguia "51 arquivos limpos" de "5 arquivos nunca analisados e 46 limpos" — o pass/fail do step é um bit só, e nem `if:`/`always()` nem `continue-on-error` (que regem se a falha de um step bloqueia *outros* steps/jobs) dizem qualquer coisa sobre **conclusão parcial dentro de um step**. Nada no modelo de `on:`/`jobs`/`continue-on-error` documentado aqui te salva de um step agregado engolindo falha por-unidade — o conserto que o projeto aplicou (laço arquivo-a-arquivo, cada iteração com seu próprio resultado contabilizado, imprimindo `encontrados`/`analisados`/`falharam` mesmo quando zero, e tratando exit 139 diferente de exit 1) é exatamente a granularidade em que `continue-on-error` opera (step/job), só que empurrada um nível abaixo, à mão, pro laço de shell do próprio step. O modelo de job/step da documentação te dá um pass/fail *por step*; ele não te dá um *por arquivo dentro de um step que processa 51 deles em lote* — isso tem que ser construído por quem escreve o fluxo, que foi o que o conserto fez.

### 2.5 `outputs` — passando dados entre steps e jobs

**EN:** Step-level: `steps.<step_id>.outputs.<name>` set via `echo "name=value" >> "$GITHUB_OUTPUT"`. Job-level: `jobs.<job_id>.outputs.<name>: ${{ steps.<step_id>.outputs.<name> }}` re-exposes a step output as a job output. Downstream job reads it via `needs.<job_id>.outputs.<name>`, and must declare `needs: <job_id>` to do so. If a reusable-workflow job producing outputs runs under a `matrix`, the final output is whichever **last successful matrix job that actually set a non-empty value** produced — an empty string from the very last successful job can shadow a real value from an earlier one. **Não confirmado na documentação** se there's a hard byte-size limit on job outputs specifically (the doc doesn't state one on this page).

**PT:** Nível de step: `steps.<step_id>.outputs.<nome>` definido via `echo "nome=valor" >> "$GITHUB_OUTPUT"`. Nível de job: `jobs.<job_id>.outputs.<nome>: ${{ steps.<step_id>.outputs.<nome> }}` reexpõe uma saída de step como saída de job. O job downstream lê via `needs.<job_id>.outputs.<nome>`, e precisa declarar `needs: <job_id>` pra isso. Se um job de fluxo reutilizável que produz saídas roda sob `matrix`, a saída final é a que o **último job da matriz bem-sucedido que de fato definiu um valor não-vazio** produziu — uma string vazia do último job bem-sucedido pode sombrear um valor real de um anterior. **Não confirmado na documentação** se há limite de tamanho em bytes específico pra saídas de job (a página não afirma um).

**EN — our practice:** `outputs:` is not used anywhere in our 6 workflows (`grep -n "outputs:" *.yml` — zero matches, matching the `needs:` finding above: no job in this repo consumes another job's data). If a future need arises (e.g. one job computing a version string that several release jobs consume), the pattern is the shared-matrix example the documentation gives: a `define-matrix` job with `outputs.colors`, consumed downstream via `strategy.matrix.color: ${{ fromJSON(needs.define-matrix.outputs.colors) }}`.

**PT — nossa prática:** `outputs:` não é usado em lugar nenhum dos nossos 6 fluxos (`grep -n "outputs:" *.yml` — zero ocorrências, batendo com o achado de `needs:` acima: nenhum job neste repo consome dado de outro job). Se surgir necessidade futura (ex.: um job calculando uma string de versão que vários jobs de release consomem), o padrão é o exemplo de matriz compartilhada que a documentação dá: um job `define-matrix` com `outputs.colors`, consumido downstream via `strategy.matrix.color: ${{ fromJSON(needs.define-matrix.outputs.colors) }}`.

## 3. Matriz de estratégia (`strategy.matrix`)

### 3.1 Sintaxe base, `include`, `exclude`, `fail-fast`, `max-parallel`

**EN:** `jobs.<job_id>.strategy.matrix` defines one or more variables, each with an array of values; the runner materializes one job per combination (Cartesian product) in a fixed enumeration order (first variable's values vary slowest). `include` either extends existing combinations (a key that doesn't conflict is merged into every matching combo) or adds a brand-new combo (when it can't be merged without overwriting a value). `exclude` removes specific combos by exact key match. `fail-fast` (default true) cancels queued/in-progress matrix jobs when one fails; `max-parallel` caps concurrently running matrix jobs regardless of runner availability. A matrix can be built dynamically from an event payload (`${{ github.event.client_payload.versions }}`) or from another job's output via `fromJSON()`.

**PT:** `jobs.<job_id>.strategy.matrix` define uma ou mais variáveis, cada uma com um array de valores; o executor materializa um job por combinação (produto cartesiano) numa ordem de enumeração fixa (a primeira variável varia mais devagar). `include` ou estende combinações existentes (uma chave que não conflita é mesclada em toda combinação que casa) ou adiciona uma combinação nova (quando não dá pra mesclar sem sobrescrever um valor). `exclude` remove combinações específicas por casamento exato de chave. `fail-fast` (padrão verdadeiro) cancela jobs de matriz enfileirados/em andamento quando um falha; `max-parallel` limita quantos jobs de matriz rodam simultaneamente, independente da disponibilidade de executor. Uma matriz pode ser construída dinamicamente a partir do payload de um evento (`${{ github.event.client_payload.versions }}`) ou da saída de outro job via `fromJSON()`.

### 3.2 Nossas matrizes, e a amarração com `CI-VERMELHO-2X`

**EN:** All 4 uses of `strategy.matrix` we have (`nightly.yml`, `distro-matrix.yml`, and two in `ci.yml`, plus two in `heavy.yml`) set `fail-fast: false` explicitly — never the default `true`. This is deliberate: a matrix meant to give independent signal per leg (e.g. `backend: [ON, OFF]`, or an OS/distro axis) is worthless if one leg's failure cancels the others before they even report; `fail-fast: false` is the correct choice for **diagnostic breadth**, at the cost of not getting an early "stop the world" signal.

**The matrix protects only what it enumerates — this is the mechanism behind `CI-VERMELHO-2X`.** Our `windows-msvc-build` job matrixes `backend: [ON, OFF]`, which correctly exercises both build configurations on Windows/MSVC. But the flag that broke both legs (`-Wno-missing-field-initializers` applied unconditionally in `glintfx/CMakeLists.txt`, `cl : command line error D8021`) was not a matrix axis at all — it was a compiler option baked into the shared build file, applied identically regardless of which matrix leg was running. A matrix enumerates the dimension you told it about (`backend`); it says nothing about a dimension you didn't declare (`platform`/`compiler`), and a shared CMake file has no matrix of its own — it's the same text compiled by whatever `runs-on`/toolchain reaches it. The root cause quoted from the incident: *"Quando o arquivo de build é compartilhado, o conjunto de plataformas a verificar é ENUMERADO, não lembrado"* — matching the documentation's own model exactly: a matrix combination is whatever you put in the `matrix:` map, full stop; nothing implicit gets added. The fix wasn't a matrix change — it was guarding the option with `$<$<NOT:$<CXX_COMPILER_ID:MSVC>>:-Wno-missing-field-initializers>`, i.e. moving the platform check from "in someone's head" into the build file itself, which is the only place a shared file *can* enumerate platforms since `strategy.matrix` doesn't reach into it.

**PT:** Todos os 4 usos de `strategy.matrix` que temos (`nightly.yml`, `distro-matrix.yml`, e dois no `ci.yml`, mais dois no `heavy.yml`) definem `fail-fast: false` explicitamente — nunca o padrão `true`. É deliberado: uma matriz feita pra dar sinal independente por perna (ex.: `backend: [ON, OFF]`, ou um eixo de SO/distro) não vale nada se a falha de uma perna cancela as outras antes mesmo delas reportarem; `fail-fast: false` é a escolha certa pra **amplitude de diagnóstico**, ao custo de não ter um sinal precoce de "parar tudo".

**A matriz só protege o que ela enumera — este é o mecanismo por trás do `CI-VERMELHO-2X`.** O nosso job `windows-msvc-build` faz matriz de `backend: [ON, OFF]`, o que exercita corretamente as duas configurações de build no Windows/MSVC. Mas a flag que quebrou as duas pernas (`-Wno-missing-field-initializers` aplicada incondicionalmente no `glintfx/CMakeLists.txt`, `cl : command line error D8021`) não era um eixo de matriz nenhum — era uma opção de compilador embutida no arquivo de build compartilhado, aplicada identicamente não importa qual perna da matriz estivesse rodando. Uma matriz enumera a dimensão que você contou pra ela (`backend`); ela não diz nada sobre uma dimensão que você não declarou (`plataforma`/`compilador`), e um arquivo CMake compartilhado não tem matriz própria — é o mesmo texto compilado por qualquer `runs-on`/toolchain que chegar nele. A causa raiz, citada do incidente: *"Quando o arquivo de build é compartilhado, o conjunto de plataformas a verificar é ENUMERADO, não lembrado"* — batendo exatamente com o modelo da própria documentação: uma combinação de matriz é o que você põe no mapa `matrix:`, ponto final; nada implícito é acrescentado. O conserto não foi mudança de matriz — foi guardar a opção com `$<$<NOT:$<CXX_COMPILER_ID:MSVC>>:-Wno-missing-field-initializers>`, ou seja, mover a checagem de plataforma de "na cabeça de alguém" pro próprio arquivo de build, que é o único lugar onde um arquivo compartilhado *consegue* enumerar plataformas já que `strategy.matrix` não alcança ele.

### 3.3 Matriz + fluxo reutilizável

**EN:** A job using `strategy.matrix` can call a reusable workflow via `uses:`, passing `${{ matrix.<var> }}` through `with:`. **Não confirmado como necessário** for us today — none of our matrices call a reusable workflow (we have none — see §8).

**PT:** Um job usando `strategy.matrix` pode chamar um fluxo reutilizável via `uses:`, passando `${{ matrix.<var> }}` por `with:`. **Não confirmado como necessário** pra nós hoje — nenhuma das nossas matrizes chama fluxo reutilizável (não temos nenhum — ver §8).

## 4. Cache de dependências

### 4.1 Cache × artefato

**EN:** Documented distinction, quoted: *"Use o cache quando quiser reutilizar arquivos que não são alterados com frequência entre execuções de fluxo de trabalho... Use artefatos quando quiser salvar arquivos produzidos por uma tarefa para usar ou visualizar após o término da execução."* A cache miss silently falls back to regenerating; an artifact is the thing itself, meant to be inspected or transferred, not regenerated. Cache content is treated as **untrusted input on restore** — never store secrets in a cached path.

**PT:** Distinção documentada, citada: *"Use o cache quando quiser reutilizar arquivos que não são alterados com frequência entre execuções de fluxo de trabalho... Use artefatos quando quiser salvar arquivos produzidos por uma tarefa para usar ou visualizar após o término da execução."* Um cache-miss cai silenciosamente pra regenerar; um artefato é a coisa em si, feito pra ser inspecionado ou transferido, não regenerado. O conteúdo do cache é tratado como **entrada não confiável na restauração** — nunca guardar segredo num caminho em cache.

### 4.2 `actions/cache` — chave, `restore-keys`, hit/miss

**EN:** `key` (max 512 chars) is looked up first for an exact match; on miss, `restore-keys` (ordered, most-specific first) are tried for **prefix** matches, returning the most-recently-created cache among partial matches. Output `cache-hit: true` only on an **exact** key match (not on a restore-keys partial match). Cache content **cannot be mutated** — a "hit" on a different key always creates a new cache entry, never overwrites. Search order for a PR from `feature` targeting `main`: exact/prefix key on `feature`, then the same on `main` (base branch) — caches are scoped to branch/tag of the run, with base-branch fallback for PRs, not workflow/job identity.

**PT:** `key` (máx. 512 caracteres) é procurada primeiro por correspondência exata; na perda, `restore-keys` (ordenadas, mais específica primeiro) são tentadas por correspondência de **prefixo**, retornando o cache criado mais recentemente entre as correspondências parciais. A saída `cache-hit: true` só em correspondência **exata** de chave (não em correspondência parcial de restore-keys). O conteúdo do cache **não pode ser mutado** — um "hit" em chave diferente sempre cria uma entrada nova, nunca sobrescreve. Ordem de busca para um PR de `feature` mirando `main`: chave exata/prefixo em `feature`, depois a mesma em `main` (branch base) — caches têm escopo de branch/tag da execução, com fallback pro branch base em PR, não identidade de fluxo/job.

### 4.3 Segurança do cache — quais gatilhos podem GRAVAR

**EN:** Only these triggers can create/overwrite a cache scoped to the default branch: `push`, `workflow_dispatch`, `repository_dispatch`, `delete`, `registry_package`, `page_build`, `schedule`. Any other trigger that resolves to the default branch — including `pull_request_target`, `issue_comment`, `workflow_run` — gets **read-only** access: it can restore, never create/overwrite; an attempted write fails silently as a step warning, not a job failure. `pull_request` itself is unaffected (its caches are already scoped to the merge ref, never the default branch).

**PT:** Só estes gatilhos podem criar/sobrescrever cache no escopo do branch padrão: `push`, `workflow_dispatch`, `repository_dispatch`, `delete`, `registry_package`, `page_build`, `schedule`. Qualquer outro gatilho que resolva pro branch padrão — incluindo `pull_request_target`, `issue_comment`, `workflow_run` — recebe acesso **só-leitura**: pode restaurar, nunca criar/sobrescrever; uma tentativa de gravação falha silenciosamente como aviso de step, não falha de job.

**EN — our practice:** every one of our 6 workflows triggers via `push`, `pull_request`, `schedule`, or `workflow_dispatch` only — all of them are in (or, for `pull_request`, orthogonal to) the trusted-write list. We have no `pull_request_target`, `issue_comment`, or `workflow_run` triggers anywhere, so the read-only-cache trap this section warns about — a workflow silently failing to update its cache forever because its trigger never had write access — cannot currently happen to us. Worth remembering if a future workflow ever reacts to a fork PR.

**PT — nossa prática:** todos os nossos 6 fluxos disparam só por `push`, `pull_request`, `schedule` ou `workflow_dispatch` — todos estão na lista confiável de gravação (ou, no caso de `pull_request`, são ortogonais a ela). Não temos gatilho `pull_request_target`, `issue_comment` nem `workflow_run` em lugar nenhum, então a armadilha de cache-só-leitura que esta seção avisa — um fluxo falhando silenciosamente em atualizar o cache pra sempre porque o gatilho dele nunca teve acesso de gravação — não pode acontecer conosco hoje. Vale lembrar se algum fluxo futuro reagir a PR de fork.

### 4.4 Limites, e a amarração com `CI-HEAVY-SEM-CACHE-DE-ACAO`

**EN:** Default 10 GB per repository (configurable up to 10 TB, extra cost beyond 10 GB), entries evicted after **7 days unaccessed** (oldest-last-accessed-first once over quota), max **200 uploads/min** and **1,500 downloads/min** per repository.

**Important distinction that our `CI-HEAVY-SEM-CACHE-DE-ACAO` finding sits right next to, and must not be confused with:** `actions/cache` (this section) caches **dependency/build content you name via `key`/`path`**. It is a **different mechanism** from how the runner fetches the **action bundle itself** (the code behind `uses: actions/checkout@<sha>`), which is downloaded from `codeload.github.com` by the runner's own action-resolution step, not through `actions/cache`. This explains why pinning actions by full commit SHA in `heavy.yml` (the correct supply-chain choice for a self-hosted runner in a public repo) and *also* using `actions/cache` for RmlUi's FetchContent tree are two independent trade-offs: fixing the cache-eviction/quota problem in §4.3–4.4 does nothing for the "ephemeral container has to re-download the pinned action bundle every run" problem, because that download isn't cache-eligible traffic in the sense this page describes — **não confirmado na documentação** whether GitHub offers any built-in mechanism to persist the downloaded action bundle across ephemeral self-hosted runner instances; the project's own candidate fixes (pre-populating `_work/_actions` at image-build time, or tolerating the occasional `codeload.github.com` timeout) are exactly the kind of workaround you'd expect given that gap.

**PT:** Padrão 10 GB por repositório (configurável até 10 TB, custo extra além dos 10 GB), entradas removidas após **7 dias sem acesso** (mais-antiga-acessada-primeiro quando acima da cota), máx. **200 uploads/min** e **1.500 downloads/min** por repositório.

**Distinção importante ao lado da qual o nosso achado `CI-HEAVY-SEM-CACHE-DE-ACAO` se senta, e que não pode ser confundida:** o `actions/cache` (esta seção) faz cache de **conteúdo de dependência/build que você nomeia via `key`/`path`**. É um **mecanismo diferente** de como o runner busca o **pacote da própria ação** (o código atrás de `uses: actions/checkout@<sha>`), baixado do `codeload.github.com` pelo próprio passo de resolução de ação do runner, não pelo `actions/cache`. Isso explica por que fixar ações por SHA completo no `heavy.yml` (a escolha certa de supply-chain pra um runner self-hosted em repo público) e *também* usar `actions/cache` pra árvore FetchContent do RmlUi são dois trade-offs independentes: consertar o problema de eviction/cota do §4.3–4.4 não faz nada pro problema de "container efêmero tem que rebaixar o pacote da ação fixada a cada execução", porque esse download não é tráfego elegível pra cache no sentido que esta página descreve — **não confirmado na documentação** se o GitHub oferece algum mecanismo embutido pra persistir o pacote de ação baixado entre instâncias efêmeras de runner self-hosted; os próprios consertos candidatos do projeto (pré-popular `_work/_actions` no build da imagem, ou tolerar o timeout ocasional do `codeload.github.com`) são exatamente o tipo de contorno que se espera dada essa lacuna.

### 4.5 Nosso padrão de cache repetido

**EN:** `ci.yml` uses the identical `cache rmlui (fetchcontent)` step shape **4 times** (jobs `build-and-test`, `build-and-test-fonteng`, `lint-and-scan`, `coverage`), each differing only in the `path` suffix and `key` suffix (`glintfx/build-${{ matrix.backend }}/_deps` / `rmlui-${{ runner.os }}-glfw${{ matrix.backend }}-...`, `-fonteng-`, `-lint-`, `-cov-`). `distro-matrix.yml` and `nightly.yml` have their own, separately-shaped cache steps. This repetition is measured evidence for §8's reuse question, not a new claim — see there.

**PT:** O `ci.yml` usa o mesmo step `cache rmlui (fetchcontent)` **4 vezes** (jobs `build-and-test`, `build-and-test-fonteng`, `lint-and-scan`, `coverage`), cada um diferindo só no sufixo de `path` e de `key` (`glintfx/build-${{ matrix.backend }}/_deps` / `rmlui-${{ runner.os }}-glfw${{ matrix.backend }}-...`, `-fonteng-`, `-lint-`, `-cov-`). `distro-matrix.yml` e `nightly.yml` têm steps de cache com forma própria, separada. Esta repetição é evidência medida pra pergunta de reuso do §8, não uma nova alegação — ver lá.

## 5. Artefatos

### 5.1 Upload/download, retenção, imutabilidade

**EN:** `actions/upload-artifact` uploads a file/dir/glob (with exclusion patterns); default name `artifact` if none given; `retention-days` sets a custom retention (cannot exceed the repo/org/enterprise-configured ceiling); default retention is **90 days** unless customized. `actions/download-artifact` fetches by name (all artifacts if no name given, each into its own directory). **Artifacts are immutable in v4** — quoted: *"Como os artefatos são considerados imutáveis em v4, é fornecida ao artefato uma entrada diferente... como nome"* when the doc's own cross-job example needs to re-upload a modified file, it must use a **new artifact name**, not overwrite the old one. Upload returns a `digest` (SHA-256); download recomputes and validates it automatically, warning (not failing) on mismatch.

**PT:** `actions/upload-artifact` sobe um arquivo/diretório/glob (com padrões de exclusão); nome padrão `artifact` se nenhum for dado; `retention-days` define uma retenção customizada (não pode exceder o teto configurado no repo/org/enterprise); retenção padrão é **90 dias** se não customizada. `actions/download-artifact` busca por nome (todos os artefatos se nenhum nome for dado, cada um no próprio diretório). **Artefatos são imutáveis na v4** — citação: *"Como os artefatos são considerados imutáveis em v4, é fornecida ao artefato uma entrada diferente... como nome"* quando o próprio exemplo entre-jobs da doc precisa reenviar um arquivo modificado, ele tem de usar um **nome de artefato novo**, nunca sobrescrever o antigo. O upload retorna um `digest` (SHA-256); o download recalcula e valida automaticamente, avisando (não falhando) em caso de divergência.

**PT/EN — our practice:** só um uso de `upload-artifact@v4` em todo o repo (`ci.yml`, um único job). Nenhum `download-artifact`. Consequência direta do achado do §2 (`needs:`/`outputs:` zero ocorrências): sem cadeia de jobs consumindo dado um do outro, o padrão de "artefato como correio entre jobs" que a documentação demonstra nunca foi necessário aqui — o único artefato existente serve pra inspeção humana pós-execução (log/binário pra baixar da UI), não pra alimentar outro job. / Only one use of `upload-artifact@v4` in the whole repo (`ci.yml`, a single job). No `download-artifact` anywhere. Direct consequence of the §2 finding (`needs:`/`outputs:` zero occurrences): with no job chain consuming one another's data, the "artifact as inter-job mail" pattern the documentation demonstrates has never been needed here — the one artifact that exists serves post-run human inspection (a log/binary to download from the UI), not to feed another job.

## 6. Containers e serviços

### 6.1 `jobs.<job_id>.container`

**EN:** `container: <image>` (or the full map form with `image`, `credentials`, `env`, `ports`, `volumes`, `options`) runs **all** the job's steps inside that Docker container instead of directly on the `runs-on` host. If omitted, steps run on the host unless an individual step is itself a container-based action (which then runs as a **sibling container**, same network/volume mounts). **Default shell inside a container is `sh`, not `bash`** — overridable via `defaults.run` or per-step `shell:`. `options` maps to `docker create` flags, but **`--network` and `--entrypoint` are explicitly unsupported**.

**PT:** `container: <imagem>` (ou a forma de mapa completa, com `image`, `credentials`, `env`, `ports`, `volumes`, `options`) roda **todos** os steps do job dentro daquele container Docker em vez de direto no host `runs-on`. Se omitido, os steps rodam no host, a menos que um step individual seja ele mesmo uma ação baseada em container (que aí roda como **container irmão**, mesma rede/montagens de volume). **O shell padrão dentro de um container é `sh`, não `bash`** — sobrescrevível via `defaults.run` ou `shell:` por step. `options` mapeia pra flags de `docker create`, mas **`--network` e `--entrypoint` são explicitamente não suportados**.

**EN — our practice:** `distro-matrix.yml` is the only workflow using `jobs.<job_id>.container` — it runs three legs (Fedora 44, Arch, Ubuntu) via matrixed `container:` images to prove our build/toolchain across distros, exactly matching the "run this job inside a specific OS image regardless of the runner's own OS" use case this feature exists for. None of our workflows use `services:` (no database/cache dependency to stand up during CI — our tests are self-contained C++/GLFW/Xvfb, not integration tests against an external service).

**PT — nossa prática:** `distro-matrix.yml` é o único fluxo usando `jobs.<job_id>.container` — ele roda três pernas (Fedora 44, Arch, Ubuntu) via imagens `container:` em matriz pra provar nosso build/toolchain nas distros, batendo exatamente com o caso de uso "rodar este job dentro de uma imagem de SO específica independente do SO do próprio runner" pra que essa feature existe. Nenhum dos nossos fluxos usa `services:` (não há dependência de banco/cache a subir durante o CI — nossos testes são C++/GLFW/Xvfb autocontidos, não testes de integração contra um serviço externo).

### 6.2 Contêineres de serviço (`services:`)

**EN:** `jobs.<job_id>.services` spins up sibling Docker containers (destroyed when the job ends) for things like a database or cache the job's steps need to reach. Access differs by where the job itself runs: **job in a container** → service reachable by its label as hostname, all ports auto-exposed between containers on the same Docker network, none exposed outside it; **job directly on the runner machine** → reach via `localhost:<port>`/`127.0.0.1:<port>`, and you must explicitly map ports with `ports:` (`8080:80`, `8080:80/udp`, or `8080/udp` for a random host port). `entrypoint`/`command` on a service override the image's own `ENTRYPOINT`/`CMD` — naming and behavior mirror Docker Compose.

**PT:** `jobs.<job_id>.services` sobe containers Docker irmãos (destruídos quando o job termina) pra coisas como banco ou cache que os steps do job precisam alcançar. O acesso muda conforme onde o próprio job roda: **job em container** → serviço alcançável pela etiqueta como hostname, todas as portas auto-expostas entre containers na mesma rede Docker, nenhuma exposta fora dela; **job direto na máquina do runner** → alcance via `localhost:<porta>`/`127.0.0.1:<porta>`, e você precisa mapear porta explicitamente com `ports:` (`8080:80`, `8080:80/udp`, ou `8080/udp` pra porta aleatória no host). `entrypoint`/`command` num serviço sobrescrevem o `ENTRYPOINT`/`CMD` da imagem — nomenclatura e comportamento espelham o Docker Compose.

**EN — flag for the security section, not mine to develop:** the documentation notes services/container jobs require a Linux runner (Ubuntu for GitHub-hosted, a Linux self-hosted machine with Docker installed for self-hosted). Our self-hosted `heavy.yml` runner is exactly that shape (containerized, Linux); its `pull_request`-trigger exclusion and supply-chain posture belong in `secao-seguranca.md`, not here — noted only so the cross-reference exists.

**PT — sinalização pra seção de segurança, não é meu escopo desenvolver:** a documentação registra que jobs de serviço/container exigem runner Linux (Ubuntu pra hospedado-no-GitHub, máquina Linux self-hosted com Docker instalado pra self-hosted). O nosso runner self-hosted do `heavy.yml` é exatamente essa forma (conteinerizado, Linux); a exclusão do gatilho `pull_request` e a postura de supply-chain dele pertencem a `secao-seguranca.md`, não aqui — anotado só pra existir a referência cruzada.

## 7. Reuso: fluxos reutilizáveis, ações compostas, ações próprias

### 7.1 Fluxos de trabalho reutilizáveis (`workflow_call`)

**EN:** A reusable workflow is a normal `.github/workflows/*.yml` file (no subdirectories supported there) whose `on:` includes `workflow_call`. It can declare `inputs` and `secrets` it expects from the caller, and `outputs` it exposes back. Three `uses:` syntaxes for a calling job: `./.github/workflows/{filename}` (same repo, same commit as the caller — no `@{ref}` allowed, contexts/expressions not allowed in this keyword), `{owner}/{repo}/.github/workflows/{filename}@{ref}` (public/private repos, `{ref}` = SHA/tag/branch; a same-named release tag wins over a branch; **SHA is documented as "a opção mais segura para fins de estabilidade e segurança"**), and `$/.github/workflows/{filename}` (same-repo shorthand, not available on GHES).

Structural limits, exact quotes: *"Você pode conectar no máximo dez níveis de fluxos de trabalho"* (top-level caller + up to 9 nested reusable levels, no loops allowed) and, from the reference page, *"Você pode chamar até 50 fluxos de trabalho reutilizáveis exclusivos por meio de um só arquivo de fluxo de trabalho"* (counting the whole nested tree from the top-level caller). Permission propagation is one-directional and non-negotiable: *"As permissões `GITHUB_TOKEN` transmitidas do fluxo de trabalho do chamador só podem ser rebaixadas (não elevadas) pelo fluxo de trabalho chamado"* — in a chain A→B→C, if A's token has `packages: read`, neither B nor C can escalate to `packages: write`. Secrets are **not** transitively passed: in A→B→C, C only gets a secret if it was explicitly forwarded A→B **and** B→C (`secrets: inherit` at each hop, or named `secrets:`). `env:` set at the workflow level does **not** propagate into a called reusable workflow, and vice versa — only declared `inputs`/`outputs`/`secrets` cross that boundary. GitHub-hosted runner assignment and billing are always evaluated against the **caller's** context, never the called workflow's repo; self-hosted runners of the called workflow are reachable only if it's in the same user/org as the caller. Re-running: re-running the whole run re-resolves a non-SHA ref; re-running only failed/specific jobs re-uses the **exact SHA from the first attempt**.

**PT:** Um fluxo reutilizável é um arquivo `.github/workflows/*.yml` normal (sem suporte a subdiretórios ali) cujo `on:` inclui `workflow_call`. Pode declarar `inputs` e `secrets` que espera do chamador, e `outputs` que expõe de volta. Três sintaxes de `uses:` num job chamador: `./.github/workflows/{filename}` (mesmo repo, mesmo commit do chamador — sem `@{ref}` permitido, sem contexto/expressão permitidos nesta chave), `{owner}/{repo}/.github/workflows/{filename}@{ref}` (repos públicos/privados, `{ref}` = SHA/tag/branch; uma tag de release com o mesmo nome vence um branch; **SHA é documentado como "a opção mais segura para fins de estabilidade e segurança"**), e `$/.github/workflows/{filename}` (atalho mesmo-repo, indisponível no GHES).

Limites estruturais, citações exatas: *"Você pode conectar no máximo dez níveis de fluxos de trabalho"* (o chamador de topo + até 9 níveis reutilizáveis aninhados, sem loops permitidos) e, da página de referência, *"Você pode chamar até 50 fluxos de trabalho reutilizáveis exclusivos por meio de um só arquivo de fluxo de trabalho"* (contando a árvore aninhada inteira a partir do chamador de topo). A propagação de permissão é unidirecional e inegociável: *"As permissões `GITHUB_TOKEN` transmitidas do fluxo de trabalho do chamador só podem ser rebaixadas (não elevadas) pelo fluxo de trabalho chamado"* — numa cadeia A→B→C, se o token de A tem `packages: read`, nem B nem C podem escalar pra `packages: write`. Segredos **não** são passados transitivamente: em A→B→C, C só recebe um segredo se ele foi explicitamente repassado A→B **e** B→C (`secrets: inherit` em cada salto, ou `secrets:` nomeado). `env:` definido no nível do fluxo **não** propaga pro fluxo reutilizável chamado, e vice-versa — só `inputs`/`outputs`/`secrets` declarados cruzam essa fronteira. A atribuição e cobrança de executor hospedado-no-GitHub é sempre avaliada contra o contexto do **chamador**, nunca do repo do fluxo chamado; executores self-hosted do fluxo chamado só são alcançáveis se ele estiver na mesma conta/org do chamador. Re-execução: reexecutar a execução inteira reresolve uma ref que não é SHA; reexecutar só jobs falhos/específicos reusa o **SHA exato da primeira tentativa**.

### 7.2 Ações compostas (`runs: using: composite`)

**EN:** A composite action packages multiple workflow steps into a single reusable step, defined by an `action.yml` (preferred filename, `.yaml` also accepted) with `runs.using: "composite"` and a `steps:` list identical in shape to a workflow's own steps. `inputs`/`outputs` are declared the same way as any action's metadata; inside the composite, `run:` steps must declare `shell:` explicitly (not inherited). `${{ github.action_path }}` gives the composite its own directory — the doc's canonical pattern is `echo "$GITHUB_ACTION_PATH" >> $GITHUB_PATH` to make a co-located script (e.g. `goodbye.sh`) callable by name from a later step. Consumed either from another repo (`uses: OWNER/repo@SHA`) or from the **same repo** via a relative path (`uses: ./.github/actions/<name>`, the recommended location, though it can live in any subfolder).

**PT:** Uma ação composta empacota vários steps de fluxo numa única etapa reutilizável, definida por um `action.yml` (nome de arquivo preferencial, `.yaml` também aceito) com `runs.using: "composite"` e uma lista `steps:` de forma idêntica aos steps de um fluxo normal. `inputs`/`outputs` são declarados do mesmo jeito que os metadados de qualquer ação; dentro da composta, steps `run:` precisam declarar `shell:` explicitamente (não é herdado). `${{ github.action_path }}` dá à composta o próprio diretório — o padrão canônico da doc é `echo "$GITHUB_ACTION_PATH" >> $GITHUB_PATH` pra tornar um script co-localizado (ex.: `goodbye.sh`) chamável por nome num step posterior. Consumida de outro repo (`uses: OWNER/repo@SHA`) ou do **mesmo repo** via caminho relativo (`uses: ./.github/actions/<nome>`, o local recomendado, embora possa morar em qualquer subpasta).

### 7.3 Comparação: fluxo reutilizável × ação composta × âncoras YAML

**EN:** Documentation's own comparison table, translated and condensed:

| aspecto | fluxo reutilizável | ação composta |
|---|---|---|
| forma | arquivo YAML em `.github/workflows/` | repositório/diretório com `action.yml` |
| pode conter jobs? | sim, vários | não — nenhum |
| log | cada job/step separado | uma única etapa no log do chamador |
| pode escolher `runs-on` próprio? | sim (é o ponto, se precisar de outra máquina) | não — roda dentro do job chamador |
| segredos | sim | não |
| publicável no Marketplace | não | sim |
| limite de aninhamento | 10 níveis / 50 fluxos únicos | até 10 ações compostas aninhadas |
| chamado de | dentro de um **job** | dentro de uma **etapa** |

A third, lighter-weight option the documentation names for reducing repetition **inside a single workflow file** (not across files): **YAML anchors and aliases** (`&anchor` / `*alias`, native YAML, not GitHub-specific) — useful when several jobs/steps share a literal config block that doesn't need to become its own callable unit.

**PT:** Tabela de comparação da própria documentação, traduzida e condensada acima. Uma terceira opção, mais leve, que a documentação nomeia pra reduzir repetição **dentro de um único arquivo de fluxo** (não entre arquivos): **âncoras e aliases YAML** (`&âncora` / `*alias`, YAML nativo, não específico do GitHub) — útil quando vários jobs/steps compartilham um bloco de config literal que não precisa virar uma unidade chamável própria.

### 7.4 Ações próprias: JavaScript, Docker, composta — e a amarração com `CI-ACTIONS-NODE20`

**EN:** Three action types, all requiring `action.yml`/`action.yaml`: **Docker container actions** (`runs.using: 'docker'`, `image: 'Dockerfile'`, `args:` maps declared `inputs` into the container's argv) — most consistent/reproducible environment, Linux-runner-only, slower (build/pull latency). **JavaScript actions** (`runs.using: node20`, `main: dist/index.js`) — run directly on the runner, work on all three GitHub-hosted OSes, faster, must be pure JS with no native binary dependency; the `@actions/toolkit` packages (`@actions/core`, `@actions/github`, etc.) exist to speed this up. **Composite actions** — covered in §7.2.

### 7.5 Versionamento de `uses:` — tags, SHA, branches

**EN:** Community action authors can version by tag, branch, or SHA; the consumer decides tolerance for automatic updates. Explicit recommendation, quoted: *"Recomendamos que você use um valor SHA ao usar ações de terceiros."* But immediately paired with the trade-off that matters for vulnerability tracking: *"Dependabot só criará Dependabot alerts para GitHub Actions vulneráveis que usam versionamento semântico."* — pinning by full SHA is the most stable/secure reference (immutable, unlike a tag which "estas são mais efêmeras e podem ser movidas ou excluídas pelo mantenedor"), but it silently opts you out of Dependabot's automatic vulnerability alerting for that action unless you also keep a human-readable version comment next to the SHA (the common `uses: actions/checkout@<sha> # v4.1.1` pattern — not something I found stated as a Dependabot requirement in the pages I read, but the natural mitigation for the trade-off the doc states). **Redirects are not supported**: if an action's owner/repo/name changes, every workflow referencing the old name breaks — a real cost of NOT pinning to a fixed identity.

**PT:** Autores de ação da comunidade podem versionar por tag, branch ou SHA; quem consome decide a tolerância a atualização automática. Recomendação explícita, citada: *"Recomendamos que você use um valor SHA ao usar ações de terceiros."* Mas emparelhada imediatamente com o trade-off que importa pro rastreio de vulnerabilidade: *"Dependabot só criará Dependabot alerts para GitHub Actions vulneráveis que usam versionamento semântico."* — fixar por SHA completo é a referência mais estável/segura (imutável, ao contrário de uma tag, que "são mais efêmeras e podem ser movidas ou excluídas pelo mantenedor"), mas te tira silenciosamente do alerta automático de vulnerabilidade do Dependabot pra aquela ação, a menos que você também mantenha um comentário de versão legível ao lado do SHA (o padrão comum `uses: actions/checkout@<sha> # v4.1.1` — não é algo que encontrei afirmado como requisito do Dependabot nas páginas que li, mas é a mitigação natural do trade-off que a doc declara). **Redirecionamento não é suportado**: se o dono/repo/nome de uma ação muda, todo fluxo que referencia o nome antigo quebra — um custo real de NÃO fixar numa identidade fixa.

## 8. Variáveis de ambiente e `defaults` (autoria de fluxo)

### 8.1 `env:` em três níveis

**EN:** `env:` scopable to the whole workflow (top-level key), a job (`jobs.<job_id>.env`), or a single step (`jobs.<job_id>.steps[*].env`) — the more specific scope wins on name collision. Runner env vars (`$NAME` on bash/Linux, `$env:NAME` on PowerShell/Windows) are interpolated **after** the job reaches the runner, so they're only usable inside `run:` steps or an action's own shell, using the syntax appropriate to that runner's shell. Contexts (`${{ env.NAME }}`) are interpolated by GitHub Actions **before** dispatch to the runner, so they're the only option in parts of the workflow that never reach the runner (e.g. an `if:` conditional).

**PT:** `env:` com escopo pro fluxo inteiro (chave de nível superior), um job (`jobs.<job_id>.env`) ou um único step (`jobs.<job_id>.steps[*].env`) — o escopo mais específico vence em colisão de nome. Variáveis de ambiente do runner (`$NAME` em bash/Linux, `$env:NAME` em PowerShell/Windows) são interpoladas **depois** que o job chega ao runner, então só são usáveis dentro de steps `run:` ou do shell da própria ação, com a sintaxe apropriada ao shell daquele runner. Contextos (`${{ env.NAME }}`) são interpolados pelo GitHub Actions **antes** do despacho pro runner, então são a única opção em partes do fluxo que nunca chegam ao runner (ex.: um condicional `if:`).

### 8.2 Variáveis de configuração (`vars` context)

**EN:** Config variables (as opposed to `env:` literals baked into the YAML) can be set at repo, environment, or org level via the web UI, and read anywhere through the `vars` context (`${{ vars.NAME }}`) — an unset config variable resolves to an empty string, not an error. Useful for parameters an org wants centrally defaulted but repo owners can override per-repo.

**PT:** Variáveis de configuração (em oposição a literais `env:` embutidos no YAML) podem ser definidas em nível de repo, ambiente ou organização via UI web, e lidas em qualquer lugar pelo contexto `vars` (`${{ vars.NAME }}`) — uma variável de configuração não definida resolve pra string vazia, não erro. Útil pra parâmetro que uma org quer padronizar centralmente mas donos de repo podem sobrescrever por repositório.

**EN — our practice:** none of our 6 workflows use `vars.*` today — **não confirmado como necessário** for a single-repo project without org-level shared parameters yet.
